## 一、三条公理

整个系统由这三条推出，其余都是推论。**公理要少，才守得住。**

| # | 公理 | 含义 |
|---|---|---|
| **A1** | **节点对等** | 每个设备都是**完整节点**，同一套功能在哪个端都可用。产品形态只决定「**怎么用**」，不决定「**能不能用**」。没有中心服务端，没有主从 |
| **A2** | **内容与呈现分离，且学科可扩展** | 知识内容是数据、展示方式是策略；**学科本身是可被第三方创作与分发的「包」** |
| **A3** | **变更留痕** | 任何改变都留下前后对比与代价；否则不许说「变好了」 |

## 二、两条**不是公理**的声明

> 用户明确指出「不适合写进公理」，所以单列。它们不是架构约束，不参与公理评审。

### 2.1 长期方向：自研 infar（基础设施）

**为什么**：若全部依赖现成组件，这个项目就只是**一个整合**，而不是**新的体系**。

**怎么放**：
- **不做公理**——它是长期工程，不是每次设计都要拿来卡的一条真理；
- **做成可替换的分层**：先用成熟组件跑通，但**每一层的接口由我们自己定义**，将来逐个换成自研实现，上层不动；
- **自研的优先级顺序**（建议，非强制）：
  1. **知识表征与学科包格式**（这是「新体系」最独有的部分，最容易做出差异）
  2. **记忆/经验的组织方式**（学习者的「不会什么」如何表征与演化）
  3. **对等节点的协作协议**（算力/内容如何在节点间流动）
  4. 底层传输、推理引擎（最后再碰，最不值得自研）

> 一句话：**接口自研，实现可以先用现成的。** 这样既保住了「新体系」，又不会被基建拖死。

### 2.2 产品立场：工具中立

- 系统提供**工具**与**方法论**（采集、OCR、解析、建树、标注、校验）；
- **这些工具怎么用、用在哪，由用户自己决定**；
- 系统**不做道德与法律的裁判者**，不内置闸门；
- 但**保留来源标注**（`origin`）：它是**便利功能**——让内容可追溯、可声明、分享时能署名。**是帮助，不是管束**。

## 四、节点对等（A1 的落地）

### 4.1 三层含义

| 层 | 规则 | 说明 |
|---|---|---|
| **功能层** | **完全一致** | 任何节点都能：建树、出题、测评、讲解、复习、同步、分发内容 |
| **表达层** | **按形态不同** | 交互与布局适配屏幕/输入方式——这是「怎么用」的差异 |
| **执行层** | **可委托** | 某节点算不动的活，**委托给邻居节点**，而不是「降级为没有」 |

> **关键区别**：v1 是「弱端没有这个功能」；v2 是「**功能都在，只是这一份活由邻居帮算**」。这才是去中心化。

### 4.2 形态差异只影响两件事

节点启动时声明一份**轻量**的形态描述（不是能力门槛）：

```jsonc
{
  "display": { "width": 480, "height": 320, "colorDepth": 16, "refreshMs": 30 },
  "input":   { "rotary": true, "buttons": 5, "touch": false, "keyboard": false, "mic": true },
  "compute": { "canRunLLM": false, "psramMB": 2, "flashMB": 8 },
  "roles":   { "alwaysOn": false, "hasRemovableStorage": true }
}
```

它只用来决定：**① 界面怎么排 ② 本地能直接算什么**。**不用来决定「有没有某个功能」。**

| 形态 | 界面的自动选择 |
|---|---|
| `rotary + 5 键` | 「旋钮翻页 ＋ 四档评分 ＋ 确认」 |
| `keyboard / 触屏` | 打字答题、滑动、批注 |
| 屏幕小 / 刷新慢 | 分页式单栏布局，不做动画 |
| `canRunLLM: false` | 讲解内容**向邻居节点请求生成**（不是没有讲解） |

### 4.3 没有中心，就没有「权威状态」

- **不设「权威节点」**。所有节点地位相同；
- 冲突用**确定性规则**解决：复习记录走**事件溯源**（天然可合并）；内容变更走**内容寻址 + 版本**（同一份内容哈希相同即等同）；
- **推论**：v1 的「弱端只上报、不裁决」被删除；v1 的「生产端独占权威」被删除。

## 五、内容与呈现分离（A2 的一半）

```jsonc
// 内容（数据层）：与"怎么展示"无关
{ "kc_id": "kc_xxx",
  "explanations": [ {"style":"intuitive"}, {"style":"formal"}, {"style":"example"} ],
  "worked_examples": [...], "misconceptions": [...] }

// 呈现（策略层）：由学科作者提供，用户/节点可切换
{ "mode": "teaching | qa", "template": "stepwise | socratic | card | drill", "params": {...} }
```

- 学科差异**只体现在策略**，不体现在数据结构 → 加一种呈现 = 加一个模板；
- `teaching / qa` 是**占位**，用户将**与各科老师商定**后再定实际分类；
- **无论最终分成几种，数据层都不改**——这就是分离的意义。

## 六、学科可扩展（A2 的另一半，v2 新增重点）

> 用户原话：「允许用户基于我们的体系和方法来新建学科，这样就不局限于我们提供的方向，也有利于建立社区」

### 6.1 学科 = 一个包

- 纯文本 / JSON 为主，**可用 Git 分发**，可被 AI 生成与校验；
- **本地私有包**与**社区公开包**用同一套规范，只是分发范围不同；
- 可**依赖**其它学科包（先修关系允许跨包）。

### 6.2 最小规范：5 个必需字段

**求小。**第一版只需这些：

```jsonc
// subject.json
{
  "id": "math.primary.g3",        // 必需：全局唯一
  "name": "小学数学三年级",        // 必需
  "version": "1.0.0",             // 必需：语义化版本
  "schema": "subject-pack/1",     // 必需：规范版本
  "license": "CC-BY-SA-4.0"       // 必需：内容许可
}
```

其余全部**可选**：`author` / `description` / `depends`（依赖的先修包）/ `presentation`（提供哪些呈现模板）/ `language` / `homepage`。

### 6.3 目录结构

```
subject/
├── subject.json      必需：元数据
├── tree/             必需：知识树（目录树 + 先修关系）
├── items/            必需：题目
├── material/         可选：教学素材（讲解、例题、常见误解）
└── templates/        可选：呈现模板
```

### 6.4 三条纪律

1. **规范要小**：能不加字段就不加。规范越大，社区越写不动；
2. **学科作者是老师，不是工程师**：写学科应当像写 Markdown + 填 JSON，而不是写代码；
3. **AI 可以生成初始包**：LLM 依据规范生成一个新学科的骨架，由人复核——这是降低创作门槛的关键手段。

## 七、工具中立与数据来源（对应第 3 条修正）

### 7.1 我们提供什么

| 工具 | 作用 |
|---|---|
| **采集** | 各种来源的获取（含爬取）——**工具本身不预设用途** |
| **OCR / 截图** ⭐ | **一等通道**：截图 → 文字 → 结构化。比爬虫更简单、适用面更广 |
| **解析** | PDF / 图片 / 网页 / 手写 → 结构化 |
| **建树** | 抽取知识点、推断先修关系 |
| **标注** | 题目 → 知识点 挂载 |
| **校验** | 答案自动校验、一致性检查 |

### 7.2 边界在哪

- 系统**只提供工具和方法论**；**怎么用由用户决定**；
- 不内置阻止性闸门，不做裁判；
- **保留来源标注**（`origin`：来源类型 / 引用 / 许可）作为**便利功能**——便于追溯、署名、分享时声明。

> **设计含义**：v1 的「同步路径只能读 `syncable` 视图」这类硬约束**移除**。取而代之的是「标注齐全，用户自行判断」。

## 八、证据账本（A3 的落地）

```
变更(学科包/策略/题目/知识树/排程参数)
   ├─ before 指标（按类别，非均值）
   ├─ after  指标
   ├─ 代价（时间/算力）
   ├─ 血统（来自哪个包/谁改的）
   └─ 裁决（采纳/拒绝）
```

**三条铁律**：追加式不可改 · 按类别记录（均值掩盖震荡）· **负结果必须留档**。

## 十、阶段

| 阶段 | 目标 | 标志 |
|---|---|---|
| ① **能装内容** | 跑通「一个学科包从无到有」 | 学科包规范可用；至少一个包能被加载与学习 |

## 14 · v2.1 增补（2026-11-02，机制补全）

> 以下六条来自用户细化，**不改变三条公理**，是公理的落地机制。

### 14.1 账号域（Account Domain）

**节点组织的基本单位不是「设备」，是「账号域」**：同一账号下的所有设备组成一个域。

| 机制 | 规则 |
|---|---|
| **计划发起** | **任何节点**都可以发起「学习计划 / 任务清单」→ 同步至**域内所有设备**。没有哪台设备是「发起机」——今天在手机上建计划，明天在单词机上也能建 |
| **`user.md` 同步** | 学习者画像在**域内**同步（每个设备都有完整副本，事件溯源合并） |
| **域边界** | 域是隐私与同步的边界：**域内自由流动，域外默认不出** |
| **权利对等** | A1 不变：发起、处理、呈现，任何节点都有权做。**没有「主设备」** |

> 一句话：**对等是权利，域是范围。**

### 14.2 委托流的第一个实例：`user-today-wrong.md`

这是 A1「执行层可委托」的**具体协议**，也是专注型节点与完整节点协作的样板：

```
[ESP32 单词机]（专注型节点）
   用户的错题（今天做错的选择题/单词）
        │ 写入
        ▼
   user-today-wrong.md          ← 纯文本，一天一文件，人可读
        │ 同步至账号域
        ▼
[域内其他节点]（手机 / 平板 / PC）
   读取 → 处理：错因归类 · 关联知识点 · 生成讲解 · 排入复习计划 · 变式题生成
        │ 结果写回
        ▼
   返回：讲解 + 复习排程 + 变式练习
        ▼
[ESP32] 呈现：下一次复习时用户直接看到处理结果
```

**为什么这个设计好**：
- **文件即接口**：`user-today-wrong.md` 是纯文本、人可读、可手改——任何设备、任何语言、任何 AI 都能处理它；
- **异步天然解耦**：单词机不等待，处理完的结果下次同步时带回；
- **每个节点做最擅长的事**：单词机做「采集错题 + 呈现」，重节点做「分析 + 生成」——**这是分工，不是分级**（见 14.6）。

### 14.3 内容策略：前置优先，OCR 兜底（修正 §7）

| 优先级 | 方式 | 说明 |
|---|---|---|
| **1（主路径）** | **我们前置制作** | 先把**大框架树**搭起来；**每个知识点收 5–10 道经典例题**；随学科包发布 |
| 2（兜底） | 当下收集 / **截图 OCR** | 运行中遇到缺口时按需补 |
| 3（社区） | 许愿式共建（§14.5） | 让别人帮我们长出长尾 |

**关键判断（用户给出）**：**整个体系树不会特别大** → **纯文本就足够**。这直接验证了学科包「纯文本 + JSON」的极简取向：不需要数据库，不需要二进制格式，Git 就是最强的内容版本管理与分发工具。

### 14.4 前置内容的最小颗粒度

```
学科包
└── 知识点（KC）
     ├── 1 份核心讲解（可后补）
     └── 5–10 道经典例题（前置必备）
          ├── 覆盖该 KC 的典型考法
          └── 含答案与解析
```

> 「5–10 道经典例题」是**内容量的基本单位**。它比「先把树做全」重要——**树是骨架，例题是肉**；只有骨架没有肉，系统无法运行。

### 14.5 共建：许愿式（降低门槛的关键）

> 用户原话：「这个部分要降低门槛，依旧是类似许愿式 + 资料就能完成的，这样发展生态比较简单」

**三级创作门槛，从低到高：**

| 级别 | 谁能做 | 做什么 | 产出 |
|---|---|---|---|
| **L1 许愿** | **任何人**（一句话） | 「我想要公务员行测·资料分析」+ 可选上传资料（教材照片/笔记/题目） | 系统生成学科包骨架 + 例题初稿 |
| **L2 修订** | 愿意花 10 分钟的人 | 对 AI 生成的内容**改错、补题、调顺序** | 修订后的学科包 |
| **L3 创作** | 老师/深度作者 | 从零编写一个包（用 §6 规范） | 原创学科包 |

**机制**：
- **许愿 = 输入（意图 + 资料）→ 系统生成 → 人工复核 → 入包**；
- 复核通过的内容**带血统**（谁许的愿、谁复核的、资料来源）——这正好接上 `origin` 标注（§7.2）与证据账本（§8）；
- **生态因此简单**：不需要人人会做包，**会提需求 + 给材料就能贡献**。L1 的门槛接近零，这是生态冷启动的关键。

### 14.6 专注型节点（调和与 A1 的关系）

> 用户原话：「ESP32 的屏幕和逻辑不同……呈现方式更适合做选择题（背单词、文科单选——语法、政治历史，考公的人也能用）……通过错题同步给其他设备处理后返回，**这种适合作为小终端而不是完整终端**」

**这条与 A1「节点对等」如何调和**——这是本节要讲清的核心：

| 概念 | 含义 | 对应 |
|---|---|---|
| **权利对等** | 任何节点**可以**发起、请求、提供任何功能 | A1（不变） |
| **擅长不同** | 每个节点**优化**自己最擅长的交互 | 本节（新增） |

**关键表述**：
> **对等是权利，专注是优化。** 专注型节点不是「低配节点」——它把**选择题式交互**做到极致（旋钮翻题、四档评分、离线可用、即开即用），而把**重处理**委托给域内邻居（§14.2）。它**可以**做讲解、做画板（权利上完全允许），只是**不优化**这件事。

**ESP32 单词机的节点画像**（据 2026-11-02 实读 `WORDO_wordmachine`，P1 已合并全部功能）：

| 项 | 实读结果 |
|---|---|
| 主控 | ESP32-S3-WROOM-1（型号后缀待定） |
| 输入 | **EC1106S 旋转编码器 + 5× 轻触键** |
| 显示 | 9 脚 2.54mm 屏接口（HDR-F_2.54_1x9P） |
| 存储 | TF-01A 卡座（离线内容） |
| 语音 | MSM261S4030H0R（I2S 麦克风） |
| 电源 | TP4056 + MT3608 + AMS1117 + SS34×3，双 LED，拨动开关 |
| 其它 | TYPE-C16P、AO3400A×2、HDR 1x4P / 1x2P |

**功能定位**（用户给定）：**选择题终端**——背单词、文科单选（语法/政治/历史）、考公刷题。错题经 `user-today-wrong.md` 委托域内处理。

### 14.7 教学工具层（v2.1 最重要的新增子系统）

> 用户原话：「需要在普通设备上提供数学画板、物理模拟等工具，可以参考希沃白板。**给模型一定的工具**，有点像手机端 DSH——有很多工具、支持新功能插件，但功能是**提供教学演示，而非开发**」

**这是什么**：模型在讲解时的**手**。没有工具的模型只能「说」，有工具的模型可以「画给看」「演给你」。

```
┌────────────────────────────────────────────────┐
│           教学工具层 Teaching Tools             │
│                                                │
│  内置工具（首批）：                             │
│   · 数学画板（几何作图、函数图像、坐标系）      │
│   · 物理模拟（受力、运动、电路）                │
│   · 化学方程式 / 实验演示                       │
│   · 时间轴 / 流程图 / 思维导图                  │
│   · 答题板 / 圈点批注                           │
│                                                │
│  机制：                                         │
│   · 工具注册表：模型可发现、可调用              │
│   · 插件化：新工具 = 新插件（社区可贡献）        │
│   · 调用结果可回放（账本留痕）                  │
└────────────────────────────────────────────────┘
```

**三条边界（用户给定，必须守住）**：
1. **面向教学演示，不是开发平台**——工具是为「把知识讲清楚」服务的，不做通用编程环境；
2. **插件有权限声明**——工具声明自己能画什么、能模拟什么，模型按需调用；
3. **工具调用进账本**——哪次讲解用了哪个工具、效果如何，可复盘（A3）。

**为什么它是自研 infar 的重要组成**（§2.1）：
- 希沃白板的护城河就是**学科工具**，不是白板本身；
- 「给模型一套教学工具运行时」在 AI 教育里**几乎没人做**——这是「新体系」而非「整合」的最有力支撑点；
- 优先级建议：在 §2.1 的顺序里，它应排在 **② 与 ③ 之间**（知识表征之后、对等协议之前）——因为它直接决定「讲解质量」这个核心体验。

### 14.8 更新后的阶段表（覆盖 §10）

| 阶段 | 目标 | 标志 |
|---|---|---|
| ① **能装内容** | 学科包规范 + **前置制作**：大框架树 + 每知识点 5–10 道经典例题 | 一个真实学科包可被加载 |
| ② **能学** | 单节点闭环 + **教学工具层 v0（至少画板）** | 一次带工具演示的完整会话留痕 |
| ③ **能记人** | `user.md` 域内同步 + 驱动重点复习 | 复习命中率有可测改善 |
| ④ **能对等** | 账号域 + **委托流（user-today-wrong.md）** | 单词机错题 → 其他节点处理 → 返回呈现 |
| ⑤ **能共建** | **许愿式**上线 | 一个外部许愿 + 资料 → 生成 → 复核 → 可用 |

> ④ 现在包含两件事：同步 + **委托**。委托流是去中心化的**体验级证明**——用户能直观感受到「设备之间在互相帮忙」。

## 15 · 模型无关与三级手册（v2.2；⚠️ 目标表述已被 §16 修正）

> ⚠️ **v2.3 修正声明**：本节写于用户澄清之前，把目标理解成「任意模型**能读懂**并处理」。用户澄清的真实目标是：**统一格式 + 统一前置提示词 ⇒ 不同模型产出效果差不多（效果趋同）**。**「能读」只是底线，「趋同」才是目标。** 请以 **§16** 为准；本节的三级手册与端侧规矩仍然有效，但降级为 §16 三件套的组成部分。

> 用户原话：「这种 user.md 因为多端同步，所以**对不同模型都要有兼容度**。我们所有的资料都要有体系。这样一个**前置的资料阅读方法.md** 可以让**任意模型**处理用户的问题。**降本嘛，不寒掺**。不过就是要**在前置做好统一架构**，**端侧也要立规矩**。」

### 15.1 原则：数据是给「任意模型」读的，不是给某个模型读的

多端同步的必然结果：**同一个域里会同时存在多个模型**——单词机上可能是个 3B 小模型，手机上是云端大模型，PC 上可能是另一家。若数据格式隐含「只有某个模型懂」，就等于把去中心化的成果拱手让给单一供应商。

**推论**：
- **设备对等（A1）的自然延伸是「模型对等」**——任何模型来都能干活，不锁定供应商；
- 手段只有一个：**数据自带说明书**。

### 15.2 「资料阅读方法.md」——随资料发布的使用说明书

**机制**：每一份数据都附带一份**人类与模型都可读的说明**，告诉任意模型：「这套文件是什么、怎么读、字段什么意思、该怎么处理、什么不能动」。这与 DSH 的 `AGENTS.md`、Anthropic 的 `SKILL.md` 是同一个范式——**把能力从模型端挪到数据端**。

**三级手册结构**：

| 层级 | 文件 | 内容 | 必需性 |
|---|---|---|---|
| **系统级** | `阅读方法.md`（每账号域一份） | 全系统文件地图 · 每类文件的作用与字段含义 · 处理规则 · **端侧规矩** · 出错怎么办 | 必需 |
| **包级** | `GUIDE.md`（每个学科包一份） | 这个包讲了什么 · 知识树怎么读 · 题目怎么用 · 呈现模板说明 · 依赖关系 | **必需**（学科包规范 §6 升级） |
| **文件级** | schema 说明 | 每类文件的可机读 schema（供校验） | 必需 |

**效果**：任意模型（包括便宜的小模型）拿到手册 + 结构化数据，就能正确处理用户的问题——**不需要为每家模型单独写 prompt，不需要微调，不需要锁定供应商**。

### 15.3 降本机制：任务分级调度

手册 + 结构化数据的直接收益是**成本**：

| 任务类型 | 例子 | 用什么模型 |
|---|---|---|
| **简单** | 错因归类、格式转换、按知识点检索、排程计算 | **本地小模型 / 最便宜的模型** |
| **中等** | 讲解生成、变式出题 | 中档模型 |
| **复杂** | 疑难答疑、跨知识点综合讲解、许愿式整包生成 | 强模型 |

**为什么小模型也能干对**：因为数据结构化 + 手册齐全——小模型不需要「理解教育」，只需要「按说明书办事」。**手册把模型能力的要求，转移到了前置的架构上。**

> 这就是「降本不寒碜」的准确含义：**成本优化的来源不是抠门，是架构。**

### 15.4 端侧规矩（节点读写纪律）

「端侧也要立规矩」——每个节点处理这些文件时必须遵守：

**读（四条）**：
1. **先读手册再读数据**——不猜字段含义；
2. **按 schema 容错读取**——字段缺失走默认行为，不报错中断；
3. **不认识的字段不删不改**——可能是更新版本的数据，本地看不懂就留着；
4. **读不懂就原样保留 + 上报**——绝不擅自「修复」。

**写（四条）**：
1. **追加式**——只追加，不改历史（`user.md` 日志段、账本、错题流同理）；
2. **校验后才落盘**——写前过 schema 校验，不过不写；
3. **只写自己该写的**——按文件的所有权划分（谁产生的文件谁主写），防止两个节点同时改同一文件；
4. **格式版本跟随**——写出的文件标注 `schema` 版本号，升级规范时旧文件不重写。

**同步（两条）**：
1. 文件级合并优先于字段级合并（简单、可靠、可预测）；
2. 冲突时**两份都保留**（`name.conflict-<节点>`），交由规则或人裁决——**绝不静默覆盖**。

### 15.5 统一架构必须在前置做好（用户强调的前提）

手册和规矩能成立的前提：**前置管线的产出就是规范的**。

| 前置产出 | 必须同时产出 |
|---|---|
| 学科包内容（树/题/素材） | `GUIDE.md` + schema |
| 用户数据结构（`user.md`/错题流） | 字段说明 + 端侧规矩条款 |
| 教学工具输出 | 工具产物的格式说明 |
| 规范变更 | **版本号递增**（`subject-pack/1 → /2`），**旧手册永久保留**（老节点还要读老数据） |

> **一句话**：**在前置多花的每一分架构功夫，都会在运行时变成任意模型的能力与真金白银的成本节约。**

### 15.6 对学科包规范的修订（§6.2 升级）

`GUIDE.md` 从可选升为**必需**（第 6 个必需项）：

```
subject/
├── subject.json      必需：5 个必需字段 + schema 版本
├── GUIDE.md          必需：本包的资料阅读方法（给任意模型和人看）★ v2.2 新增
├── tree/             必需
├── items/            必需
├── material/         可选
└── templates/        可选
```

> 字段可以少，**手册不能缺**——「规范要小」与「体系要全」不矛盾：字段少是降低**创作**门槛，手册全是保障**消费**质量。

## 16 · 统一格式与跨模型一致性（v2.3，修正并深化 §15）

> 用户澄清原话：「我的意思是 我们的数据需要按照一种同一的格式来写 让多种模型在吃到前置提示词后再读取后面的资料出来的效果能差不多 而不是这个意思 这个统一的格式和架构是需要设计的」

### 16.1 目标重述（取代 §15.1 的表述）

| | 表述 |
|---|---|
| ❌ v2.2 理解（底线） | 任意模型**能读懂**数据 |
| ✅ 真实目标 | **同一份前置提示词 + 同一份统一格式数据 → 不同模型产出效果差不多** |

**「效果差不多」的判定标准**（必须先定，否则没法验收）：

| 维度 | 判定方式 | 要求 |
|---|---|---|
| **结构化字段** | 机器比对（两份输出逐字段 diff） | **必须一致** |
| **语义内容** | 人工抽检（等价即通过） | 等价即可 |
| **文风/措辞** | — | **允许差异区**（本来就不该强行统一） |

> 把「效果差不多」从一句感觉变成**可验收的标准**，是本节第一件事。

### 16.2 统一架构三件套（需要正式设计的核心交付物）

用户点明「这个统一的格式和架构是需要设计的」——它是**正式的设计交付物**，不是文档里几段话：

| # | 交付物 | 回答什么 | 版本化 |
|---|---|---|---|
| **1** | **统一数据格式** | 数据**怎么写**（字段、结构、必填项、禁写项） | `subject-pack/N` |
| **2** | **统一前置提示词** | 模型**怎么被喂**（**一份**，所有模型共用——**不是每家模型各写一套**） | `prompt-pack/N` |
| **3** | **统一输出 schema** | 产出**怎么验**（字段固定、枚举优先、顺序固定） | `output-schema/N` |

三者**同版本发布、互相引用**，合起来是一个「规范包」。**缺一件，「效果趋同」就不成立**：格式不统一→读法各异；提示词不统一→理解各异；输出不统一→没法比对也没法验收。

### 16.3 为什么效果能趋同：把模型的自由度一层层收窄

模型间差异来自「自由发挥的空间」。架构的作用就是**收窄自由度**：

| 自由度 | 收窄手段 |
|---|---|
| **读什么** | 数据按统一格式组织；前置提示词写明文件地图 |
| **怎么处理** | **规程化步骤**——逐步骤写明做什么、禁止什么（是「步骤 1→2→3」，不是「请你理解一下」） |
| **输出什么** | **统一输出 schema**——字段固定、枚举优先于自由文本、顺序固定 |
| **风格漂移** | **示例即 few-shot**——规范自带每类任务 2–3 个标准输出示例（这是对齐跨模型效果最有效的单一手段） |

> **规律：格式越明确 ⇒ 模型差异越小 ⇒ 越敢用便宜模型。** §15.3 的降本由此才**建立在可靠前提上**——不是「小模型大概能行」，而是「一致率实测达标后接入」。

### 16.4 前置提示词的结构：一份文本，两种消费

```
prompt-pack/N
├── ① 角色与目标            固定
├── ② 处理规程              固定（步骤化）
├── ③ 输出 schema           固定
├── ④ 端侧规矩              固定（含「不得改写本提示词」）
├── ⑤ 阅读方法.md 正文       注入（文件地图 + 字段词典）
└── ⑥ 标准示例              few-shot（每类任务 2–3 个）
```

**一份文本，两种消费**：
- **人读** = 资料阅读方法（手册）；
- **模型吃** = 前置提示词（系统提示词正文）。

**单一事实源**——手册与提示词**不会漂移**，因为它们是同一份东西。v2.2 里「手册」和「提示词」被当成两个东西，v2.3 合并。

### 16.5 一致性验证循环（本节最重要的方法论）

**统一格式不是纸面设计出来的，是「测」出来的。**

```
选 N 个模型（强 / 中 / 弱 各若干）
   + 同一份 prompt-pack + 同一份数据
   → 跑同一批任务
   → diff 输出（结构化字段机器比对 + 语义人工抽检）
   → 差异归类：
        语义差异   ⇒ 格式欠约束   → 收紧该处的格式/规程
        字段缺失   ⇒ schema 欠规定 → 补字段
        文风差异   ⇒ 允许区，不动
   → 发布 prompt-pack（版本 +1）→ 重测
```

**收敛判据**：当**弱模型与强模型的结构化输出一致率达标**（如 ≥95% 字段一致）时，该任务类型的格式即「收敛」，方可放心接入便宜模型。

每一次验证**进账本**（A3）：哪版格式、哪些模型、一致率多少、改了什么。

> 这就把「格式设计」从拍脑袋变成**实测驱动**：**差异处 = 格式欠约束处**，diff 就是设计图纸的修改意见。

### 16.6 端侧规矩补充（接 §15.4）

新增第 9 条：**端侧不得改写前置提示词**。提示词是统一架构的一部分，随数据版本走；端只能**选择用哪一版**，不能改内容。

### 16.7 设计工作量（诚实说明）

这是一项**正式工程**：格式规范、提示词、输出 schema、**一致性测试脚本**、一致性报告，都要迭代。建议**并入阶段①**，不单独立项：

> 做第一个最小学科包时，**同步**产出 `prompt-pack/1` 与 `output-schema/1`，并用 3 个模型跑第一轮一致性测试。**用最小包当格式设计的试验田**——最小包上每一处「模型间差异」，就是格式要收紧的地方。
