## 0. 一句话架构

**一个「知识树为骨架、双端同步为动脉、FSRS 排程为心跳、自产内容为血肉」的四端学习系统；权威数据留在本机，可分发内容与授权内容在结构上物理隔离。**

```
                    ┌───────────── 权威层（只在本机，永不外发）─────────────┐
                    │  教材/题库抓取数据（origin.redistributable = false）  │
                    └───────────────────────┬──────────────────────────────┘
                                            │ 只读参考
   前置阶段（离线一次性 + 可增量）            ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │  资料管线：解析 → 结构化 → 知识点抽取 → 题目挂载 KC → 知识树落库   │
   └───────────────────────────────┬────────────────────────────────────┘
                                   ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │  共享层（可同步/可分发的知识资产）                                  │
   │  知识树（目录树 + KC DAG 分表） · 自产题目 · 教学材料 · 索引        │
   └───────────────────────────────┬────────────────────────────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  ┌───────────┐            ┌───────────┐            ┌──────────────┐
  │ Windows   │            │ iOS/iPadOS│            │ ESP32-S3     │
  │ (主力/生产)│            │ (主用/学习)│            │ 单词机(弱端) │
  └─────┬─────┘            └─────┬─────┘            └──────┬───────┘
        │                        │                         │
        └────────── 同步层（复习事件流 + 知识资产增量）──────┘
                                   ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │  私有层（每用户本地，永不上传）                                    │
   │  用户模型 user.md · 复习状态(FSRS S/D/due) · 答题记录 · 错题       │
```

## 1. 设计原则（每条都由调研结论推导，不是偏好）

| # | 原则 | 依据 | 反面做法（禁止） |
|---|---|---|---|
| **P1** | **权威数据与可分发内容物理隔离**，隔离由**代码强制**而非流程约定 | 需求基线 §7.3；资料 12 §建议 | 靠"记得别上传"来保证合规 |
| **P2** | **用户答题数据本地优先、绝不上传** | 资料 12 §建议；PIPL 第 31 条 | 云端存原始答题记录 |
| **P3** | **移动端是「弱常驻客户端」**，不做后台常驻与 P2P 节点 | 资料 03 §6.1（Android 15+ 前台服务 24h 内 6h；iOS BGProcessingTask ≈60s） | 让手机后台挂着同步 |
| **P4** | **P2P 按「约 30% 连接走中继」做容量规划**，中继池必须可自托管 | 资料 03 §4.3（DCUtR 实测 70%±7.1%，非厂商自述的 90%） | 假设「去中心化不需要服务器」 |
| **P5** | **进化押在技能/内容/工作流层，不押在权重层** | 资料 02 §② 六层光谱：强证据全在 L0–L3 | 一上来做分布式训练/全参数微调 |
| **P6** | **度量先于功能**：先有账本与指标，再谈「变强」 | 资料 06 §一 | 先做效果宣称，再补度量 |
| **P7** | **先做朴素基线**：记忆检索先做 Raw-RAG，被证明更优才上复杂方案 | 资料 06 §四 反例 1（Raw-RAG 在 7 设置中 6 个第一） | 默认 GraphRAG/多级记忆更优 |
| **P8** | **知识树「目录」与「先修」分表** | 资料 13 §①（章节随教材改版重排，先修关系不变） | 把先修边挂在章节节点上 |
| **P9** | **知识点粒度只拆不合，第一版故意偏粗** | 资料 13 §①（粗可后验拆，细无法后验合并） | 一上来做到最细粒度 |
| **P10** | **绝不自研基础设施**：P2P 用 Iroh、推理用 llama.cpp、排程用 FSRS | 资料 05 §5.3 不做清单 | 自己写打洞/通信压缩/间隔重复算法 |
| **P11** | **跨端只同步「小状态 + 增量 + 事件流」**，大对象走内容寻址 | 资料 03 §6.4（CRDT 文档膨胀） | 同步整棵知识树/整份词库 |
| **P12** | **每个「采纳」必须留下证据**（前后对比 + 代价 + 血统） | 资料 06 §六 adopt/reject 协议 | 改了就算数，不留痕 |

## 3. 数据架构：三层 + 合规隔离

### 3.1 三层定义

| 层 | 内容 | 存储位置 | 可同步 | 可开源/分发 |
|---|---|---|---|---|
| **权威层** | 抓取的教材原文、题库原题 | **仅本机私有库** | ❌ **代码强制禁止** | ❌ |
| **共享层** | 知识树、自产题目、教学材料、外部资源索引 | 本地 + 可同步 | ✅ | ✅（用户决定） |
| **私有层** | `user.md` 画像、FSRS 状态、答题记录、错题 | 每用户本地 | ⚠️ 仅同用户多端 | ❌ |

### 3.2 合规开关（结构性约束）

```sql
-- 每一条内容都必须声明来源与可分发性
CREATE TABLE content_origin (
  content_id      TEXT PRIMARY KEY,
  source_type     TEXT NOT NULL,      -- 'scraped' | 'generated' | 'user_note' | 'licensed'
  source_ref      TEXT,               -- 来源 URL / 生成模型 / 授权编号
  redistributable INTEGER NOT NULL,   -- 0 | 1
  CHECK (source_type <> 'scraped' OR redistributable = 0)  -- ★ 抓取内容永不可分发
);

-- 同步与导出路径必须显式过滤（视图而非约定）
CREATE VIEW syncable_content AS
  SELECT * FROM content WHERE redistributable = 1;
```

> **要点**：任何同步/导出/P2P 广播的代码路径**只能**读 `syncable_content` 视图，不直接读 `content` 表。这把合规从「记得别传」变成「结构上传不出去」。依据：资料 12 §建议②。

### 3.3 存储选型

| 用途 | 选型 | 依据 |
|---|---|---|
| 客户端主库（Win/Android/iOS） | **SQLite** + 物化 `kc_ancestors` 闭包表 | 资料 13 §①（DEXA 2026 实测：深度≤3 子图查询 SQLite 874s vs Neo4j 8757s） |
| 弱端（ESP32） | **CSR 扁平数组 + 字符串池**，按 section 分片，附先修祖先摘要 | 资料 13 §①（500 KC ≈ 30–80 KB；避免在 MCU 上跑 SQLite） |
| 知识资产版本管理 | **Git**（内容寻址 Merkle DAG） | 资料 02 §⑦（commit=个体、分支=格、remote=岛、merge=迁移） |
| 大对象（词库/音频/图片） | 内容寻址 + 分片 | 资料 03 §建议 3 |

## 4. 核心数据模型

### 4.1 知识树：目录树与 KC DAG **分表**

```sql
-- ① 目录树（随教材改版会重排 —— 易变）
CREATE TABLE toc_node (
  toc_id     TEXT PRIMARY KEY,   -- 稳定不透明 ID，不用"第3章第2节"这类含序号的
  parent_id  TEXT REFERENCES toc_node(toc_id),
  subject    TEXT NOT NULL,      -- 学科
  book       TEXT,               -- 教材版本
  title      TEXT NOT NULL,
  ordinal    INTEGER,            -- 排序，允许变
  depth      INTEGER NOT NULL
);

-- ② 知识点（KC）—— 相对稳定
CREATE TABLE kc (
  kc_id       TEXT PRIMARY KEY,  -- ★ 不透明稳定 ID（改版不变），见 §4.4
  name        TEXT NOT NULL,
  aliases     TEXT,              -- JSON 数组
  difficulty  REAL,
  bloom_level TEXT,              -- 认知层次
  measurable  INTEGER DEFAULT 1  -- 是否可测
);

-- ③ KC ↔ 目录 多对多（改版只影响这张表，不动 KC）
CREATE TABLE kc_toc (
  kc_id  TEXT REFERENCES kc(kc_id),
  toc_id TEXT REFERENCES toc_node(toc_id),
  PRIMARY KEY (kc_id, toc_id)
);

-- ④ 先修 DAG（与目录解耦 —— 这是本项目最关键的建模纪律）
CREATE TABLE kc_edge (
  from_kc    TEXT REFERENCES kc(kc_id),   -- 先修
  to_kc      TEXT REFERENCES kc(kc_id),   -- 后继
  strength   TEXT CHECK(strength IN ('hard','soft')),  -- 硬/软先修
  reason     TEXT,                        -- 一句人话，供人工复核
  evidence   TEXT,                        -- 来源：专家/LLM/数据挖掘 + 票数
  PRIMARY KEY (from_kc, to_kc)
);

-- ⑤ 物化祖先闭包（查询加速，构建期生成）
CREATE TABLE kc_ancestors (
  kc_id       TEXT, ancestor_id TEXT, depth INTEGER,
  PRIMARY KEY (kc_id, ancestor_id)
);
```

> **schema 依据**：资料 13 §② 与 §③（已一手核实 Marble `os-taxonomy` 的 `dependencies.json`：`{topicId, prerequisiteId, strength: hard|soft, reason}`，3941 条边、opaque 稳定 ID —— **这份最简 schema 直接可抄**）。

### 4.2 题目 schema

```jsonc
{
  "item_id": "it_xxx",
  "type": "single_choice | multi_choice | fill_blank | short_answer | judge",
  "stem": "...",                       // 题干（支持 LaTeX）
  "options": [{"key":"A","text":"..."}],
  "answer": "...",
  "analysis": "...",                   // 解析
  "difficulty": 0.62,                  // 0-1 或 IRT b 参数
  "kc_ids": ["kc_xxx", "kc_yyy"],      // ★ 必须挂 KC，否则诊断链路断裂
  "origin": {
    "source_type": "generated",        // scraped | generated | user_note | licensed
    "source_ref": "model:xxx@v1",
    "redistributable": true
  },
  "verification": {                    // 自产题必须走过的校验
    "answer_checked_by": "solver@v1",  // 自动解题校验
    "human_reviewed": false,
    "reviewed_at": null
  }
}
```

> **⭐ 第一验收指标**：`item_coverage = 已挂 KC 的题目数 / 总题目数 ≥ 0.85`。
> 依据：资料 13 §① —— **题目没挂 KC，整个诊断链路就是断的**；且挂载过程本身就是树的体检（挂不上题的 KC = 太细，抢题的 KC = 太粗）。

### 4.3 用户模型（`user.md` 式）

采用**人类可读 + 机器可解析**的 Markdown（front-matter 存结构化字段）。范式借鉴 ReMe 的「记忆即文件」（Apache-2.0）与 AutoSkill 的 `SKILL.md`。

```markdown
---
user_id: u_xxx
updated_at: 2026-10-27T12:00:00+08:00
schema_version: 1
---

# 学习者画像

## 学科概览
| 学科 | 已学知识点 | 掌握率 | 最近学习 |
|---|---|---|---|
| 数学 | 42 | 0.68 | 2026-10-26 |

## 薄弱知识点（自动 + 手动）
| kc_id | 名称 | 掌握度 θ | 错题数 | 标记来源 | 备注 |
|---|---|---|---|---|---|
| kc_0a1 | 分数通分 | 0.31 | 7 | auto | 用户自述"总是搞混" |

## 学习偏好
- 呈现方式偏好：图文优先 / 例题优先
- 单次时长：25 分钟（番茄钟）
- 复习时段：早 7-8 点
- 已否决的讲解风格：纯公式推导（2026-10-20）

## 学习日志（追加式，勿改历史）
- 2026-10-26 数学/分数：测评 12 题对 8，讲解后复测 12 对 10
```

> **设计要点**：
> 1. **人类可读可编辑**——用户可以自己改（这是「个性化设置」的字面要求）。
> 2. **追加式日志段不可改写**——历史是证据，也是日后「实验」的对照（对齐资料 06 的账本思想）。
> 3. `kc_id` 与知识树共享 ID 空间 → 「记录什么不会」直接落在知识树节点上，天然支持重点复习与根因定位。

### 4.4 复习状态（FSRS，设备端）

```jsonc
{
  "card_id": "cd_xxx",
  "kc_id": "kc_0a1",
  "item_id": "it_xxx",     // 可选：卡片可绑定具体题目
  "S": 12.5,               // 稳定性
  "D": 6.2,                // 难度
  "due": "2026-11-02T07:30:00+08:00",  // ⚠️ 绝对时间戳 → 依赖可信时间源
  "last_review": "2026-10-26T07:35:00+08:00",
  "reps": 5, "lapses": 1
}
```

**同步协议（决策）**：
- 设备只上报**复习事件流**：`(card_id, ts, rating)`，约 **8–12 字节/条**；
- 手机/PC **重放合并**为权威状态；
- 回写 `(card_id → S, D, due)` 快照给设备。
- ⚠️ **必须先解决时间源**：FSRS 的 `due` 是绝对时间戳，设备离线期间会漂移 → 用 SNTP，或在同步时由手机写入软时钟。
> 依据：资料 11 §⑦ 建议 2。**device-local FSRS 是本架构里性价比最高的一条决策**——单词机离线可背，同步量极小。

### 4.5 ID 稳定性（改版不破坏历史）

| 对象 | ID 策略 |
|---|---|
| KC | **不透明稳定 ID**（如 `kc_0a1b2c`），由创建时生成，**永不复用** |
| 目录节点 | 同样用不透明 ID（不用「第3章」这类含序号的） |
| 教材改版 | 只改 `kc_toc` 映射，`kc` 与 `kc_edge` 尽量不动 |
| KC 合并 | 保留 `merged_into` 指向新 ID，历史记录**迁移而非删除** |

> 依据：资料 13 §① 与 §C11。

## 5. 关键流程

### 5.1 前置阶段：资料管线（离线，Windows 端）

```
① 采集
   ├─ 路径 1：公开知识点 + 官方资源在线引用（不进库）
   └─ 路径 4：权威数据抓取 → 进「权威层」，redistributable = 0
        ⚠️ 硬约束：不触碰任何反爬绕过（详见需求基线 §7.3 ②）

② 解析
   PDF/EPUB/扫描件 → 文本（含公式、图表的处理）

③ 结构化
   题干 / 选项 / 答案 / 解析 / 难度 → 统一 schema

④ 知识点抽取（LLM + schema 约束）
   教材目录 → 章节 → KC（第一版故意偏粗，每小节 2–7 个 KC）
   ⚠️ 幻觉与过抽取须人工校验

⑤ 题目挂载 KC  ← ★ 最该先做的一步
   规则 + 检索 + LLM 分类 → 人工抽检
   验收：item_coverage ≥ 0.85

⑥ 先修关系推断（三路线投票）
   知识驱动(LLM/专家) + 数据驱动(答题序列挖掘) + 结构驱动(章节顺序/共现)
   → kc_edge，每条带 strength 与 reason

⑦ 质量红线
   kt_auc_delta = AUC(KC树标签) − AUC(章节粗标签) > 0
   若 ≤ 0 → 改树，而不是改算法

⑧ 落库 + 生成弱端裁剪包（CSR）
```

> 依据：资料 13 §②.5/§④/§⑤/§⑦。

### 5.2 运行时：一次学习会话

```
用户选「学科 → 部分」
     ▼
拉取：该部分的 KC 子图 + 题目 + 教学材料
     ▼
测评定标（CAT / IRT / Elo 在线更新）
     ▼
掌握度估计（BKT → DKT 双层；详见资料 04 §⑤）
     ▼
根因定位：若某 KC 错 → 沿 kc_edge 回溯先修祖先 → 找真正缺失的下层
     ▼
选题策略：先修 DAG + ZPD + FSRS 到期压力 三者并联
     ▼
教学呈现（按 KCs / 学科选择模板：教学类 或 问答类 —— 见 §5.3）
     ▼
复测 → 更新掌握度 → 写入 user.md → 排下一次复习
     ▼
记录到证据账本（前后对比 + 代价）
```

> 依据：资料 04 §⑤（BKT/IRT/FSRS/先修 DAG+ZPD 伪代码齐备）、资料 13 §⑤（根因定位算法）、资料 06 §六（账本）。

### 5.3 教学呈现层（可插拔，对应需求「两大类」）

需求原文：「不同学科有不同的呈现方式 到时候我再决定 大概是有 教学类和问答类两大类区分」

**架构决策：把「内容」与「呈现」分离。**

```jsonc
{
  "knowledge_material": {          // 数据：一份知识点的教学素材（与呈现无关）
    "kc_id": "kc_0a1",
    "explanations": [ {"style":"intuitive","content":"..."},
                      {"style":"formal","content":"..."},
                      {"style":"example_first","content":"..."} ],
    "worked_examples": [...],
    "common_misconceptions": [...],
    "media": [...]
  },
  "presentation_policy": {          // 策略：可插拔、按学科/用户偏好选择
    "mode": "teaching | qa",
```

> **为什么这样切**：需求明确教学方式**尚未决定**。把呈现做成策略层，未来加一种学科呈现方式只需加一个 template，**不动数据与后端**。
> 备选增强：**教学类**可接文档 08 的「人机互学」——让用户向 AI 讲解，用「可教学性分数」评价（基于 NeurIPS 2024 的 LbT，免训练仅提示即可显著提升；⚠️ 该分数为本项目原创设计，需先在 P1 验证是否成立）。

### 5.4 同步流程（多端）

```
[任一端本地变更]
     ▼
产生增量（事件流 / 知识资产 diff）
     ▼
按 P 4 选路径：局域网直连 → Iroh 打洞(~70%) → 中继兜底
     ▼
冲突处理：
  · 复习事件流 → 事件溯源重放（天然无冲突）
  · 知识资产 → CRDT（仅小状态）或 Git merge（大对象）
     ▼
合并出权威状态 → 回写各端快照
```

> 依据：资料 03 §建议 3/§6.4、资料 11 §⑦ 建议 2。
> ⚠️ **移动端只在「用户主动打开 App」时同步**，不依赖后台任务（依据 P3）。

## 8. 分阶段实施路线

> 排序原则：**风险由低到高、每阶段都能独立演示、优先打通数据链路**。

| 阶段 | 目标 | 交付物 | 关键验收 |
|---|---|---|---|
| **S0 · 数据筑基** ⭐最先 | 知识树建起来 + 题目挂上 KC | 知识树 DB + 挂载好的题库 | `item_coverage ≥ 0.85`；`kt_auc_delta > 0` |
| **S1 · 最小闭环（单机）** | 选章节 → 测评 → 讲解 → 复测 | Windows 端可跑通一次会话 | 一次会话的完整账本 |
| **S2 · 用户模型** | `user.md` 记录「什么不会」→ 重点复习 | 画像文件 + FSRS 排程 | 复习命中率 / 延迟测试有提升（**如实记录负结果**） |
| **S3 · 多端** | iPadOS/Android 端可学习 | 移动端 App | 移动端冷启动同步可用 |
| **S4 · ESP32 端** | 单词机离线自主排程 + 同步 | 固件（独立工作区） | 离线背词 → 同步 → 状态一致 |
| **S5 · 跨端同步** | P2P 同步知识资产增量 | Iroh 通道 + 中继池 | 两设备离线各自变更后可合并 |
| **S6 · 可选增强** | 人机互学（可教学性分数）/ 内容自进化 | 实验性功能 | 必须先通过 06 的度量标准才允许宣称 |

### 明确「不做」清单（防止项目膨胀）
1. ❌ 不自研 P2P / NAT 打洞 → 用 Iroh
2. ❌ 不自研通信压缩优化器 → 用 SparseLoCo/DisTrO，且**本阶段不做分布式训练**
3. ❌ 不从零训练基座模型 → 用现成量化模型
4. ❌ 不做区块链/代币激励
5. ❌ 不做 3D 化身/社交空间
6. ❌ 不在移动端做后台常驻
7. ❌ 不宣称「AI 自进化」——除非通过文档 06 的账本标准

## 9. 度量与验收（内置，不是事后补）

| 层 | 指标 | 来源 |
|---|---|---|
| **学习效果（人的）** | 掌握度提升、**延迟测试**保留率、迁移测试正确率 | 资料 04 |
| **系统学习能力（AI）** | `ACC` / **遗忘 `F`** / `AULC` / `TUE` | 资料 06 §三 |
| **知识树质量** | `item_coverage`、`kt_auc_delta`、人工抽检一致率 | 资料 13 |
| **记忆检索** | 必须以 **Raw-RAG 基线**为门槛 | 资料 06 §四 反例 1 |
| **人机互学（若做）** | 可教学性分数、反哺增益、双向留存 | 资料 08 §3.3 |
| **账本** | 追加式、per-category、记录代价与血统 | 资料 06 §六 |

> 三条禁止：**不用 LLM 自评做唯一判据**、**不看单一均值**（均值掩盖震荡）、**不在测试集上做演化**。

## 10. 合规设计（结构性）

| 措施 | 实现 |
|---|---|
| 抓取内容永不外发 | `content_origin` CHECK 约束 + `syncable_content` 视图（§3.2） |
| 不触碰反爬 | 管线中**不存在**验证码识别/登录绕过的代码路径；遇阻即停并记录 |
| 限速与退避 | 采集端强制 rate limit + 失败退避 + 单机串行 |
| 答题数据本地化 | 私有层永不上传（P2） |
| 未成年人保护 | 若多用户，需监护人同意 + 专门处理规则（PIPL 第 31 条） |
| 开源边界 | 只开源 `core/` 的**处理逻辑**与**通用采集框架**；站点适配规则不入库 |
| 许可证 | 建议起步 **AGPL-3.0**（详见资料 07 §三）⚠️ 引入依赖前逐个核实，注意 PaddleOCR/MinerU/Docling/Marker 可能存在 AGPL/GPL 传染 |

## 11. 风险登记（Top 8）

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | **题目→KC 覆盖率不达标** | 诊断链路断裂，系统退化为「按章出题」 | S0 先做；粒度只拆不合 |
| 2 | **`kt_auc_delta ≤ 0`**（树没带来增量信息） | 知识树白建 | 把该指标当质量红线，改树不改算法 |
| 3 | **合规**：抓取内容的边界 | 法律风险 | 见 §10；`redistributable` 强制开关 |
| 4 | **移动端后台限制** | 同步体验受损 | P3：只在打开 App 时同步 |
| 5 | **中继成本** | 30% 连接走中继 | 自托管中继池，按 70% 规划 |
| 6 | **ESP32 Flash/PSRAM 规格未定**（N8R2 vs N8R8 vs N16R8） | 影响 TTS/双 OTA/词库并存 | ⚠️ 见需求基线 §8.3 问题① |
| 7 | **屏驱动 ST7365 库支持未验证** | 可能点不亮 | 下单前实测 |
| 8 | **效果无法证明** | 无法宣称价值 | 先用确定性 grader 跑通最小闭环；**允许如实记录负结果** |
