## 一、「数形结合」落盘方案：文本为源，索引派生

> 用户原话：「数据落盘可以考虑数形结合 考虑一下有没有好的方式 以纯文本为主」
> ⚠️ 「数形结合」是我的解读：**结构化数据（数）与文本叙述（形）结合使用**，以纯文本为源。如理解有偏请纠正。

### 1.1 三层结构

```
源层（Source）      纯文本：MD / JSON / MD+YAML —— 唯一事实源，Git 管理
   │ 重建（rebuild 命令）
索引层（Index）     SQLite 单文件 —— 加速查询，可随时删除重建，无损失
   │ 加载
运行层（Runtime）   内存对象 —— 会话引擎使用
```

**核心纪律：源层永远手写/机器可写可读；索引层永远可重建。** 索引坏了就删掉跑 `rebuild`，零损失。

### 1.2 格式选择规则（一句话能记住）

| 数据形态 | 用什么 | 例 |
|---|---|---|
| **能枚举的**（字段固定、值离散） | **JSON** | 题目、知识点、复习事件、设置 |
| **长篇叙述的**（讲解、解析、笔记） | **Markdown** | 教学素材、错题讲解 |
| **两者都有**（条目带元数据+正文） | **MD + YAML front-matter** | user.md、卡片、知识点讲解 |

### 1.3 与「任意模型可读」的衔接（框架 §15/16）

- 三种格式**都是纯文本** → 任何模型直接读；
- 每类文件配 `_schema`（JSON Schema）→ 模型吃了 prompt-pack 后**按 schema 校验**输出；
- 人工可用任意编辑器改 → 改完跑 `rebuild` 同步索引。

## 二、同步矩阵（逐类数据定规则）

> 用户原话：「考虑怎么同步各种数据」——本节是核心交付。

### 2.1 矩阵总表

| # | 数据 | 源格式 | 谁产生/修改 | 变更模式 | **合并规则** | 同步时机 | 量级 |
|---|---|---|---|---|---|---|---|
| 1 | **学科包**（树/题/素材） | JSON+MD | 前置管线、许愿生成、人工修订 | 版本化、追加为主 | **内容寻址**：哈希相同即同版；包级 semver；升级只进不退 | 包发布时 | MB |
| 2 | **user.md**（画像） | MD+YAML | 域内所有节点 | 追加（日志段）+ 少数字段更新 | **日志段=事件溯源按时间合并；画像字段=最新者胜，冲突双保留** | 打开 App 时 / 定时 | KB |
| 3 | **复习状态**（S/D/due） | JSONL 事件流 | 全部节点 | **只追加** | **事件溯源重放**（天然无冲突） | 打开时 | 小 |
| 4 | **学习计划/任务清单** | MD+YAML（每计划一文件） | **任意节点发起** | 条目增删 + 状态翻转 | 条目增删=操作级合并；状态=完成事件溯源 | 变更即广播 | 小 |
| 5 | **错题流** | `wrong/<日期>-<节点>.md` | 主要是专注节点 | 只追加 | **文件名自带日期+节点 → 天然不冲突** | 产生后尽快 | 小 |
| 6 | **处理结果**（讲解/变式） | JSON+MD | 重节点 | 一次生成 | 按**请求 ID** 关联；新版本覆盖旧（带时间戳） | 处理完即推 | 中 |
| 7 | **证据账本** | JSONL | 所有节点 | 只追加 | 追加合并（无冲突） | 随同步 | 增长 |
| 8 | **设置/模型配置** | JSON | 本机 | 覆盖式 | **API key 默认不同步**（可开启，开启则用域密钥加密）；其余设置域内 LWW | 手动 | 小 |

### 2.2 为什么大部分数据「天然无冲突」

设计上刻意让 **大多数数据只追加**（3/5/7 + 2 的日志段）：追加型数据合并=并集，**数学上就不可能冲突**。真正需要裁决的只剩两处：
- user.md 的画像字段（谁最后改的算谁的，冲突双保留人工看）；
- 学习计划的并发编辑（条目级合并，极少发生）。

> **同步设计的最高原则：能靠「只追加」消灭的冲突，绝不靠算法解决。**

### 2.3 错题委托流的完整文件路径约定

```
domain/
├── packs/                          ← 学科包（#1）
├── users/
│   ├── u_main/
│   │   ├── user.md                 ← 画像（#2）
│   │   ├── reviews/events.jsonl    ← 复习事件（#3）
│   │   ├── plans/                  ← 学习计划（#4）
│   │   └── wrong/
│   │       └── 2026-11-02_esp-a1.md ← 错题流（#5，日期_节点）
│   └── u_second/...                ← 第二账户（#多账户）
├── processed/                      ← 处理结果（#6，按请求 ID 组织）
├── ledger.jsonl                    ← 证据账本（#7）
└── settings.json                   ← 设置（#8）
```

## 三、账号域：建立、加入、多账户

### 3.1 密钥与身份

| 对象 | 机制 |
|---|---|
| **节点身份** | 每台设备生成 **Ed25519 密钥对**；`node-id` = 公钥指纹。设备间通信默认端到端加密 |
| **域身份** | 创建域时生成**域密钥对**；`domain-id` = 公钥指纹 |
| **入域** | 新设备显示/扫描**配对码**（含 domain-id + 一次性加入令牌 + 发现信息）→ 域内设备签名确认 → 成员资格落盘 |
| **退域/除名** | 需**域密钥签名**的撤销指令 |

> ⚠️ **诚实说明**：成员管理需要一个签名权威（域密钥持有者）。这与 A1「无主从」不矛盾——**管理权 ≠ 架构分级**：任何节点都能发起同步、处理、教学；只有「谁能加入/退出」这一件事需要密码学上的权威。这是安全必需，无法用对等协议替代。

### 3.2 多账户（默认单人，可添加）

| 机制 | 规则 |
|---|---|
| **profile** | 每个账户 = `users/<u_id>/` 一个目录 + 一份 `user.md` |
| **默认** | 创建域时自动建 `u_main` |
| **添加** | 设置里「添加账户」→ 起名 + 设密码 |
| **切换** | 锁屏式切换：选 profile → 输该 profile 的密码（**PBKDF2 本机校验**） |
| **密码** | **仅存本机、绝不同步**（新设备上为某 profile 设密码需重新设置）——同步的是数据，不是凭据 |
| **隔离** | 切换后，会话/复习/错题全部读写该 profile 目录 |

## 四、模型接入规范（纯 API）

### 4.1 设置项

```jsonc
{
  "providers": [
    { "preset": "deepseek",            // 内置预设（见 4.2）
      "baseURL": "https://api.deepseek.com/v1",
      "apiKey": "sk-...",              // 本机加密存储，默认不同步
      "models": ["deepseek-chat", "deepseek-reasoner"] },
    { "preset": "custom",              // 自定义 OpenAI 兼容端点
      "baseURL": "https://your-gateway/v1",
      "apiKey": "...", "models": ["..."] }
  ],
  "tiers": {                           // 任务档位 → 三元组映射（用户可改）
    "fast":   { "provider": "deepseek", "model": "deepseek-chat",     "effort": "low" },
    "normal": { "provider": "deepseek", "model": "deepseek-chat",     "effort": "medium" },
    "deep":   { "provider": "deepseek", "model": "deepseek-reasoner", "effort": "high" }
  }
}
```

### 4.2 思考强度的适配（各家参数不同 → 适配器翻译）

| 档位 | OpenAI | DeepSeek | 通义 | Anthropic |
|---|---|---|---|---|
| 快速 low | `reasoning_effort:"low"` | `deepseek-chat` | `enable_thinking:false` | 不开 extended thinking |
| 标准 medium | `reasoning_effort:"medium"` | `deepseek-chat` | `enable_thinking:true` | 短 thinking budget |
| 深度 high | `reasoning_effort:"high"` | `deepseek-reasoner` | 思考 + 更多 token | 长 thinking budget |

> 预设清单：DeepSeek / 通义千问 / Kimi / 智谱GLM / OpenAI / Anthropic / Gemini / OpenRouter / 自定义。预设只包含 baseURL 与默认模型列表，**key 由用户填**。

### 4.3 对一致性验证的影响（框架 §16.5 修订）

- 测试模型全部为 **API 模型**（无本地模型）；
- 首轮组合：**1 强（深度档）+ 1 中（标准档）+ 1 另一家的标准档**——跨提供方比跨参数更能暴露格式问题。
