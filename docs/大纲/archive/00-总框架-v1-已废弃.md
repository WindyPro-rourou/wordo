# 总框架 v1

> **性质**：大框架（架构骨架）。**故意不含硬件细节与算法选型**——那些由用户自行判断。
> **日期**：2026-10-27 ｜ **状态**：待评审
> **为什么这样写**：端硬件在本项目里一直在变（20 键机械键盘 → 5 键 + 旋钮，就发生在两天内）。**任何把硬件细节写进核心的设计都会很快作废**，所以本框架的第一条公理就是「端无关」。

---

## 一、五条设计公理

整个系统的形态由这五条推出，其余都是推论。

| # | 公理 | 含义 | 为什么 |
|---|---|---|---|
| **A1** | **端无关** | 核心只认识「能力」，不认识「设备」。端通过声明自己的能力接入 | 硬件在变。20 键 → 5 键 + 旋钮，若核心依赖按键数就全盘重做 |
| **A2** | **内容与呈现分离** | 知识内容是数据；怎么展示是可插拔的**策略** | 需求原文：「不同学科有不同的呈现方式，到时候我再决定」——没定的事不能写进数据 |
| **A3** | **权威与分发分离** | 授权/抓取的数据在**结构上**无法进入同步与导出路径 | 合规不能靠"记得别传"，要靠代码强制 |
| **A4** | **度量内建** | 每一次「采纳/变更」都留下前后对比与代价 | 没有账本就没有「变强」，只有感觉 |
| **A5** | **只做编排，不自研基建** | P2P、推理、排程、存储全部用现成的 | 个人项目的死法第一名是「把基建当主业」 |

> 这五条同时是**评审标准**：任何新功能如果违反其中一条，先讨论公理是否要改，而不是直接加功能。

## 三、核心机制：能力契约（A1 的落地）

这是整个框架**最关键的一处设计**，也是应对「硬件一直在变」的唯一手段。

### 3.1 端不描述自己是什么，只声明自己能做什么

```jsonc
// 每个端启动时向核心注册一份能力声明（示例值仅作说明，非定稿）
{
  "endpoint_id": "esp-wordcard-v1",
  "display": {
    "width": 480, "height": 320, "colorDepth": 16,
    "refreshMs": 30,            // 刷新耗时；>1000 则框架自动禁用动画/滚动
    "partialRefresh": false,
    "sunlightReadable": false
  },
  "input": {
    "rotary": true,             // 旋钮（可滚动/翻页/调节）
    "tactileButtons": 5,        // 轻触键数量
    "touch": false,
    "keyboard": false,
    "voice": true               // 是否有麦克风
  },
  "compute": {
    "canRunLLM": false,         // 能否本地跑语言模型
    "psramMB": 2, "flashMB": 8,
    "maxModelMB": 0
  },
  "storage": { "internalMB": 0, "removable": true },
  "network": { "wifi": true, "ble": true, "alwaysOn": false },
  "power":   { "batteryMah": 1000, "alwaysOn": false },
  "sensors": { "mic": true, "speaker": false, "haptic": false }
}
```

### 3.2 核心按能力自动裁剪（不需要为每个端写一套逻辑）

| 能力声明 | 框架自动行为 |
|---|---|
| `rotary: true, tactileButtons: 5` | 映射为 **「旋钮翻卡 + 四档评分 + 确认」** 交互 —— 恰好对应间隔重复的四档评分语义 |
| `tactileButtons >= 8` 或 `keyboard: true` | 启用打字式答题与全键盘捷径 |
| `touch: true` | 启用滑动手势、手写批注（iPadOS） |
| `refreshMs > 1000` 或 `colorDepth <= 4` | 按 A2 自动切到**单色分页模板**，禁用动画、进度条、秒表 |
| `canRunLLM: false` | 教学呈现降级为「预生成内容 + 卡片化」，不请求本地生成 |
| `canRunLLM: true, psramMB >= 8` | 允许本地生成讲解、变式题、即时答疑 |
| `alwaysOn: false` | 同步策略切换为「打开时同步」，不做后台常驻 |
| `mic: true` | 开放语音相关功能（朗读跟读 / 口述答题） |
| `speaker: false` | 发音类功能降级为「显示音标」 |

> **效果**：端从 20 键换成 5 键 + 旋钮，**核心代码一行不用改**。这就是 A1 的价值，也是对「硬件还在改」这件事的工程回应。

### 3.3 契约的三条纪律

1. **端只声明，不协商**：核心不向端索取未声明的能力。
2. **能力缺失必须降级，不得崩溃**：每个功能都要有「最低能力要求 + 降级路径」。
3. **契约必须可测试**：一份能力声明应能驱动出一套自动化 UI 冒烟测试（端形态再多也测得过来）。

## 四、内容与呈现分离（A2 的落地）

```jsonc
// 内容（数据层）：与"怎么展示"完全无关
{
  "kc_id": "kc_xxx",
  "explanations": [ {"style": "intuitive", "content": "..."},
                    {"style": "formal",    "content": "..."},
                    {"style": "example",   "content": "..."} ],
  "worked_examples": [...],
  "misconceptions": [...],     // 常见错误理解
  "media": [...]
}

// 呈现策略（策略层）：按 学科 / 学习者偏好 / 端能力 选择
{
  "mode": "teaching | qa",
  "template": "stepwise | socratic | card | drill",
  "params": { "hint_depth": 2, "show_answer_first": false }
}
```

**三条规则**：
1. **学科差异只体现在策略，不体现在数据** —— 加一个学科呈现方式 = 加一个 template，不动后端。
2. **同内容多策略并存** —— 同一知识点可以既有「教学类」也有「问答类」的表达。
3. **策略选择要记账** —— 哪个策略对哪个学习者更有效，进账本（A4）。

> 需求原文「大概是有教学类和问答类两大类区分」→ 落到框架里就是 `mode` 的两种取值，**未来无论细化成几种，都不改数据层**。

## 五、三层数据与合规边界（A3 的落地）

```
┌─────────────────────────────────────────────────────────────┐
│ 权威层 Authoritative   （抓取/授权的教材与题库原题）          │
│  · 只在本机   · redistributable = 0   · 永不进同步/导出      │
└───────────────────────┬─────────────────────────────────────┘
                        │ 只读参考
┌───────────────────────▼─────────────────────────────────────┐
│ 共享层 Shared          （知识树 · 自产题 · 教学素材 · 索引）  │
│  · 可同步   · 可分发   · 用户决定是否开源                    │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│ 私有层 Private         （user.md · 掌握度 · 复习状态 · 错题） │
│  · 仅同用户多端同步   · 绝不上传第三方                       │
└─────────────────────────────────────────────────────────────┘
```

**结构性强制（不是流程约定）**：
- 每条内容带 `origin.redistributable` 字段，抓取来源在 schema 层被 `CHECK` 约束为 0；
- 同步/导出/P2P 的代码路径**只能读 `syncable` 视图**，物理上读不到权威层；
- 这条纪律的收益：**合规从「人的记性」变成「类型系统的约束」**。

## 六、贯穿机制：证据账本（A4 的落地）

任何「变更」都必须是一条可审计记录：

```
变更(技能/策略/题目/知识树/排程参数)
   ├─ before 指标（按类别，非均值）
   ├─ after  指标
   ├─ 代价（时间 / 算力 / token）
   ├─ 血统（从哪来、基于谁）
   └─ 裁决（采纳 / 拒绝 + 谁决定的）
```

**三条铁律**：
1. **追加式**，历史不可改；
2. **按类别记录**（均值会掩盖剧烈震荡）；
3. **负结果必须留档** ——「这周没进步」是一条合法且有价值的记录。

> 账本是 A4 的载体，也是**唯一能支撑「变强了」这句话的东西**。没有它，任何效果宣称都不成立。

## 七、扩展点：加东西时改哪里

| 要加什么 | 改哪里 | 不需要动 |
|---|---|---|
| **新学科** | 知识基底加数据 + 可选新呈现策略 | 核心、端 |
| **新呈现方式** | 实现一个 `PresentationTemplate` | 数据层、后端 |
| **新端**（新手表/新读卡器） | 写一份能力声明 + 一个渲染器 | 核心、其它端 |
| **新题型** | 实现一个 `ItemType` 处理器 | 会话引擎主体 |
| **新调度算法** | 替换 `Scheduler` 实现（接口不变） | 其余全部 |
| **新数据源** | 加一个管线适配器 + 声明 `origin` | 运行时 |

> **判据**：如果加一个东西需要改「核心」，说明抽象错了，先修抽象。

## 八、端的分工原则（与具体硬件无关）

| 角色 | 职责 | 谁适合 |
|---|---|---|
| **生产端** | 跑前置管线、维护知识树、生成与校验内容 | 算力强、常驻的机器（通常是 Windows） |
| **主力学习端** | 长时学习、讲解呈现、笔记批注 | 大屏、输入丰富（iPadOS 优先） |
| **随身学习端** | 碎片化做题、随时复习 | 手机 |
| **专注复习端** | 单词/卡片式高频复习，离线可用，低干扰 | 专用设备（ESP32 单词机一类的弱端） |
| **权威状态持有者** | 合并各端变更、裁决冲突 | 生产端（单点，其余端只是上报） |

**两条硬约束**：
- **弱端只上报、不裁决**——避免在算力受限设备上做冲突合并；
- **移动端不做后台常驻**——同步只在用户打开 App 时发生。

## 九、分阶段（大阶段，不含细节）

| 阶段 | 目标（一句话） | 完成的标志 |
|---|---|---|
| **① 内容站得住** | 知识树建起来，题目挂上知识点 | 题目挂载率达标；树能带来超出「按章节」的信息量 |
| **② 单机闭环** | 在一台机器上跑通「选内容 → 测评 → 讲解 → 复测」 | 一次会话留下完整账本 |
| **③ 会记人** | `user.md` 记录「他不会什么」并驱动重点复习 | 复习命中率有可测量的改善（**允许负结果**） |
| **④ 多端** | 手机/平板可学习，变更多端可合并 | 两端离线各自变更后可正确合并 |
| **⑤ 弱端** | 专用设备离线可用并同步 | 离线复习 → 同步 → 状态一致 |
| **⑥ 可选增强** | 人机互学 / 内容自进化等实验能力 | **必须先通过账本标准才允许对外宣称** |

**顺序不可颠倒的理由**：①②③ 是「这个系统有没有价值」，④⑤ 是「用起来方不方便」。先把价值做出来。

## 十、不做清单（框架级边界）

1. ❌ 不自研 P2P / 打洞 / 通信压缩
2. ❌ 不从零训练基座模型
3. ❌ 不做区块链 / 代币激励
4. ❌ 不做 3D 化身 / 社交空间
5. ❌ 不在移动端做后台常驻
6. ❌ 不把硬件细节写进核心（违反 A1）
7. ❌ 不在缺少账本的情况下宣称任何效果

## 十一、风险（框架级）

| 风险 | 说明 | 框架内的应对 |
|---|---|---|
| **端形态继续变** | 已经发生过一次剧变 | A1 能力契约（§3） |
| **知识树建了但没用** | 挂了 KC 却没有增量信息量 | 把「树是否带来超出章节的信息」当质量门槛，不过就改树 |
| **效果无法证明** | 学习类系统的通病 | A4 账本；允许负结果；不用自评做判据 |
| **合规** | 授权数据的边界 | A3 结构强制隔离 |
| **呈现方式迟迟不定** | 需求方明确说「到时候再定」 | A2 内容与呈现分离（§4），不定也不阻塞 |
| **项目膨胀** | 四端 + 弱端 + AI 功能，容易失控 | 分阶段（§9）+ 不做清单（§10） |

## 十二、观察记录：端硬件现状（仅供参考，框架不依赖）

> **读取时间**：2026-10-27 14:35 ｜ **来源**：嘉立创 EDA 云端工程 `esp-wrodcard`（用户正在修改中，**以下随时可能过时**）
> 记录目的：证明 A1 的必要性 —— 该设计与两天前的 `esp32_multitool`（20 键机械键盘）已完全不同。

| 原理图页 | 器件数 | 关键器件（读到的库名） |
|---|---|---|
| P1 主控 | 8 | ESP32-S3-WROOM-1-N8R2（8MB Flash / 2MB PSRAM）、Type-C-16P、去耦电容、10k、2×5.1k（Type-C CC） |
| P2 电源 | 25 | TP4056-42-ESOP8（充电）、MT3608（升压）+ 22µH + SS34×3、AMS1117-3.3（LDO）、XH 电池座、电源开关、双 LED、分压电阻组 |
| P3 外设 | 15 | 9 脚 2.54mm 屏接口、TF-01A 卡座、**MSM261S4030H0R（I2S 数字麦克风）**、S8050×2、1x6 / 1x4 排针、1N4148WS |
| P4 输入 | 6 | **5× 轻触键（1TS009C）+ EC11 旋转编码器** |

**框架层面的观察**（不含设计意见）：
- 端从「20 键机械键盘」变为「5 键 + 旋钮」→ 若核心依赖按键数，此刻就要重写。**这正是 A1 的用例**。
- 出现 I2S 麦克风 → 能力契约里的 `sensors.mic` 已有位置，无需改框架。
- 出现 9 脚屏接口 → 屏的具体驱动、分辨率、色彩深度**都只影响该端的能力声明**，不影响核心。
- 「5 键 + 旋钮」与「四档评分 + 翻页」的匹配度天然很高，属于契约自动映射的典型场景（§3.2），**框架已覆盖**。

> ⚠️ 以上为**事实记录**，不含硬件设计建议。硬件细节与选型由用户自行判断。

## 十三、这份框架刻意没做的事

为避免越界（用户已明确：框架之外由他自己判断），本框架**不包含**：

- ❌ 具体算法选型（间隔重复算法、知识追踪模型）
- ❌ 具体技术栈（框架、语言、库）
- ❌ 硬件设计与器件选型
- ❌ 知识树的具体 schema 与字段
- ❌ 同步协议的报文格式
- ❌ 教学方式的具体分类

这些属于**实现细节**，已在 `docs/资料/`（14 份调研）与 `docs/大纲/01-详细设计参考-v0.1.md` 中另有材料，供需要时取用。
