# WORDO 可扩展性专项评审

## 1) 用户自助新建学科（scaffold_pack → 入库填内容）够不够用？

**结论：对“会动手的老师”勉强够用，对学生和“只想用”的老师不够，且路径断点在入库而非建包。** scaffold_pack 生成骨架本身门槛低，但真实工作量在后面：老师手里是 PPT/试卷照片，不是入库管线要求的教材/OCR/出卷 JSON 三种规范输入，“建包 5 分钟、填内容卡 2 天”是典型弃用点。学生自助建包则几乎必然产出结构烂的树，污染后续 SRS/薄弱页逻辑。

**可执行建议：**
- 在 scaffold_pack 里补一个 `validate --strict` 出口，骨架生成后立即校验并给出“距可运行还差几步”的 checklist，让用户知道离“能出题”有多远。
- 增加一条最小内容路径：允许直接粘贴一段文本（一章一节），用现有跨模型 Schema 拆出“知识树节点 + 3 道题”入库，作为入库管线的“第 0 档”入口——比要求规范 JSON 现实得多。
- 学生建包时强制走模板预设（如“语文古诗词”“英语单词”），禁止从空树开始；老师建包才开放自由树。

## 2) 入库管线最容易在哪出错、怎么防？

**最易错的三处：OCR 静默错字、知识树层级歧义、题目-答案错位。** OCR 把“过氧化钠”识别成“过氧化铀”这类错误一旦入账本，SRS 会围绕错误内容训练，且 append-only 让修正成本高；知识树拆分主观性最强（同一章 AI 每次拆法不同），会破坏后续“薄弱页”聚合；出卷网 JSON 里题干/选项/答案/解析字段不规范时，最容易整段错位入库且校验可能只验 Schema 不验语义。

**可执行建议：**
- 所有入库内容打 `source_confidence` 标记进账本；OCR 内容必须先过一遍“结构校验 + 抽样人工确认”（至少每批抽 N 题），低置信题目入库后打 `needs_review`，不出题给用户。
- 知识树拆分必须挂 golden 用例：固定 2-3 份真实教材样本，入库结果做快照对比，AI 拆树口径变了 CI 直接红——你已有跨模型 golden 机制，直接复用，别让入库是这套机制的豁免区。
- 入库校验加语义断言：答案必须在选项集合内、题干长度下限、知识点引用必须命中树中存在的 node_id（ dangling 引用是最常见的静默失败）。
- 给账本预留“入库批次”概念：一个批次可整体作废重建（逻辑回滚），否则 OCR 批量错一次就没法收回。

## 3) ESP32 只做取题/写 JSON/搬运的隐患

**主要隐患是离线冲突和时钟不可信。** mininode 设备必然长时间离线，多设备各自 append 后合并时，你桌面端的“单调 seq”模型在设备侧很难维持——两台 ESP32 都产 seq=5 时靠什么定序？其次，ESP32 没有 RTC 电池、断电后时间归零，SRS 间隔计算（4h/24h 倍增）基于时间戳，错的时间戳会直接毁掉复习队列，且这些账本行是“搬运”合并进主账本的，错误会永久沉淀。

**可执行建议：**
- 设备侧账本行不要带本地 seq，改为“设备 ID + 原子计数器 + 时间戳（标 `clock_untrusted: true`）”，合并进主账本时由桌面端重排序、重算 SRS，设备永远不产生权威时间。
- 合并必须幂等：同一行多次搬运不能重复入账（用 hash 去重），这是搬运式架构最常见的静默 bug。
- ESP32 上加最小校验：写入前对单行 JSON 做 hash，桌面端合并时验证——你已有 verify_ledger，把这条链路接进去，别让最弱设备成为账本完整性的豁免端。
- 明确文档声明 ESP32 是“只读作答终端”，禁止它承载任何学习决策（判分/复习调度全在桌面端），防止后续有人在固件里加逻辑。

## 1) 自助建学科：空骨架 ≠ 可用学科

- **问题**：「空骨架」在 chat-first 交互里几乎没有实际作用——学生第一句话判到该学科后，没有节点可讲、没有题可出、没有东西进 SRS；老师那边又必须自己运行 `tools/ingest`（教材或 OCR）才有内容。「生成骨架」和「产生内容」之间缺少一个面向非技术用户的入口。
- **建议 A（补最小可用内容）**：scaffold 生成的包默认内置「starter 内容」——3–5 个知识节点 + 每个节点 3–5 道题 + 每节点一段示例讲解，且这些内容必须能通过现有 golden 用例与 `verify_ledger` 的结构校验。目标是**新学科创建当天就能完成一次完整交互循环**（讲解→出题→判分→进复习队列），用此验证 scaffold 契约本身没问题。
- **建议 B（把 ingest 降级为向导）**：先只支持最小路径「粘贴一段文本 → 自动抽 3 个节点 + 5 道题 → 预览改动 diff → 确认入库」，OCR、出卷网 JSON 作为进阶入口。向导产出统一写入 `candidate/` 待审区，禁止直接改正式包。
- **建议 C（建治理，否则会碎片化）**：加 `pack_id + version + 迁移脚本` 字段，并提供「合并学科 / 导入他人包 / 删除学科但保留账本」三个操作。没有合并能力，一年后用户的学科列表会变成一堆同义包，跨包节点的复习记录也无法迁移。
