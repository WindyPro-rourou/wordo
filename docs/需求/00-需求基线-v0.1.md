## 二、结构化解读

### 2.1 产品形态

一个**多端教学 + 测试系统**，四类端，各自分工（分工为用户初步意向，待细化）：

| 端 | 定位（初步推断） | 备注 |
|---|---|---|
| **Windows** | 主力端：内容生产、知识树维护、长时学习/做题、数据管理 | 前置爬取与资料加工大概率也在此 |
| **Android** | 移动端：碎片化学习、随时做题 | |
| **iOS / iPadOS（为主）** | 移动端主力：**以 iPadOS 为主**——暗示重视大屏手写/阅读体验（iPad + Pencil 做笔记/做题） | |
| **ESP32 单词机（自创）** | **专用弱端**：单词/卡片式记忆与复习，随身、低功耗、可能离线 | 全新且强约束的一端 |

### 2.2 资料管线（前置、离线、一次性 + 可增量）

```
[前置阶段，不在应用运行时]
  爬取教材原文  ──┐
  爬取题库题目  ──┤（用户指定来源举例：出卷网等，按知识点对应）
                 ▼
        按章节切分 / 结构化为「知识点 + 题目」
                 ▼
           生成完整知识树
                 ▼
          落库（储备资料）

[运行时]
  用户选择 学科 → 部分
        ▼
  调取：该部分的知识点 + 题目 + 知识树
        ▼
  测评 → 讲解 → 按用户需求教学
```

**关键含义**：
- 资料是**静态储备**，不在运行时爬 → 对运行时性能友好，但**前置加工质量决定整个系统上限**。
- **「按章节区分」是知识树的第一层来源**（教材目录即骨架）。
- 「相对应知识点的题目」→ **题目必须能挂到知识点上**，这是题库与知识树的连接点。

### 2.3 运行时学习循环

`选学科/部分` → `拉取知识点+题目+知识树` → `测评` → `讲解` → `按需教学` → （回到测评）

这正是文档 `06-度量与验证` 与 `04-学习科学与知识表征` 所描述的闭环，**但现在有了明确的落地形态**：以教材章节与知识树为骨架。

### 2.4 教学方式（待定）

用户明确：**不同学科不同呈现方式，到时再定**；初步分为两大类：
- **教学类**（讲知识）
- **问答类**（出题、答疑、对话）

→ 因此系统需要一个**「教学内容呈现层」的抽象**：把「知识点 + 讲解素材 + 题型」作为数据，把「怎么呈现」做成可插拔的模板/策略，而不是把某一种形式写死。

### 2.5 自学习 = 用户个性化模型（重要澄清）

> 「关于自学习：这个是关于使用用户的个性化设置 制作类似 user.md 记录什么是用户不会的 之后再重点复习这样的」

**这是对项目定位的一次重要澄清，且大幅降低了风险**：

| | 之前调研理解 | 用户实际想要 |
|---|---|---|
| 「自学习」指的是 | AI 自我进化（改 prompt / 技能 / 权重） | **用户的**个性化学习记录 |
| 载体 | 技能库 / LoRA / MAP-Elites 归档 | **类似 `user.md` 的用户画像文件** |
| 内容 | 系统自己变强 | **记录「用户不会什么」→ 之后重点复习** |
| 可验证性 | 全行业未解（文档 06 的 P0-1） | ✅ **可验证**：答题正确率、延迟测试、复习命中率 |

**含义**：
1. 文档 06 的 **P0-1「自进化能否证明有效」不再阻塞本项目**——因为用户要的核心是**可测量的用户学习效果**，而非 AI 自我进化。
2. 文档 04 的结论（「人的学习是价值锚点，有硬实证」）与用户的意图**完全吻合**。
3. `user.md` 这种**人类可读的 Markdown 画像**，与调研中发现的 **AutoSkill 的 `SKILL.md` 范式**、**ReMe 的「记忆即文件」范式**高度同构 → **可以直接借鉴**（AutoSkill 许可待核实，ReMe 是 Apache-2.0）。
4. 「记录什么不会」在算法上正是 **知识点级掌握度（BKT/DKT）+ FSRS 排程**，文档 04 §⑤ 已给出公式。
5. AI 侧的「自我进化」可降级为**可选增强**（技能/提示词层，L0–L2），不再是项目成立的先决条件。

## 七、决策记录：资料路线

### 7.1 用户原话

> 「1+4就好了 4是权威数据嘛 到时候我们只是自用 开源只开系统里面的处理部分 只提供爬虫工具 写个仅供学习就行 这个好搞」

### 7.2 解读

用户选择 **路径 1（自产为主 + 官方资源在线引用）＋ 路径 4（仍要爬取权威数据）** 的组合：
- **保留爬取**，理由是**权威数据**（教材与题库的质量优于 LLM 自产）；
- 定位为**纯自用**；
- **开源边界**：只开源「系统里的处理部分」+ 提供**爬虫工具**；
- 用「**仅供学习**」声明作为说明。

### 7.3 ⚠️ 风险记录（必须随决策一起存档）

> 以下不是反对意见，而是**为了让这个决定能被安全执行**而必须写下来的事实。原话与决策已如实记录，不修改。

**① 「仅供学习」声明本身不产生法律豁免。**
免责声明不能把侵权变为合法。真正可依托的是《著作权法》第 24 条**个人学习、研究**的合理使用情形——但其边界是**不得向公众提供**（第 24 条(六)明确「不得出版发行」，且须通过三步检验法）。所以「自用」这个定位本身是**有效的**，而「写个仅供学习」这句声明是**无效的**——有效的是行为边界，不是文字。

**② 真正的刑事红线是「突破技术措施」，不是「爬」。**（这是「能做」与「绝不能做」的分界）

| 行为 | 性质 |
|---|---|
| 正常 HTTP 请求、遵守 robots、限速、不登录/不破解、数据仅本地自用 | 🟡 民事层面风险（自用可主张合理使用）；**不构成刑事** |
| **破解验证码、绕过登录墙、伪造身份、规避反爬安防** | 🔴 **刑事**——晟品案（2017）京0108刑初2384号：认定「规避或突破安防措施、未经许可进入系统＝侵入」，构成**非法获取计算机信息系统数据罪** |

**→ 硬性约束：抓取过程绝不触碰任何反爬绕过手段。一旦需要破解才能拿到数据，就说明这条路到此为止。**

**③ 公开提供「针对特定站点的爬虫」比自己爬风险更高。**
自己抓取 = 个人使用；公开分发指向特定商业站点的抓取脚本，可能被认定为**帮助他人侵权**。
**建议调整**：开源**通用抓取框架与接口**（站点适配规则由使用者自行填写、不入库），而不是开源「针对出卷网/学科网的现成脚本」。这与用户「只提供爬虫工具」的初衷一致，但把风险降了一档。

**④ 工程上把合规做成「结构约束」而非「流程约定」**（来自文档 12 §建议）：
- schema 增加 `origin.redistributable` 字段，并做成**代码层强制开关**：非授权来源的数据在技术上**无法**进入同步 / 导出 / P2P 分发路径；
- 抓取内容**默认只进本地私有库**，与「自产内容」「用户笔记」物理隔离（不同表 / 不同目录）；
- 抓取限速、失败退避、单机串行。

### 7.4 这条决策对架构的影响

| 影响 | 说明 |
|---|---|
| ✅ **自动满足** | 四端分发的只是「系统 + 自产内容」，权威数据永远留在本机 |
| ✅ **与文档 12 路径 A 不冲突** | 路径 1 与路径 4 可以**共存**：自产题用于「可分发/可同步」的部分，抓取数据用于「本地学习」的部分 |
| ⚠️ **题库版权** | 抓取内容**不得**进入 P2P 同步、导出、开源发布等任何对外路径 |
| ⚠️ **未成年人数据** | 若多用户使用，答题数据建议「本地优先、绝不上传」（PIPL 第 31 条） |

### 8.2 与文档 11 结论的对照（哪些被证实、哪些要修正）

| 文档 11 的结论 | 与实际设计的对照 |
|---|---|
| 首选 ESP32-S3 + PSRAM | ✅ **一致** |
| 屏幕：E-ink 省电、刷新慢、有残影 | ⚠️ **不适用**——实际选的是 **3.5" TFT 全彩**。TFT 的约束完全不同：**背光耗电是主要矛盾**（已有 PWM 调光 + 寝室模式降亮的设计），但没有残影/刷新惩罚，UI 可以做动画 |
| UI 定死「翻页 + 4–6 个物理键」 | ⚠️ **过保守**——实际有 **20 键**，可做「百词斩式」交互、快捷操作、模式切换组合键 |
| 词库用「索引 + 数据分离」（抄 SIPI2 + ECDICT） | ✅ **仍然成立**，且已有 TF 卡可直接落地 |
| FSRS 放设备端、同步只交换事件流 | ✅ **强烈建议采纳**——但当前需求写的是「艾宾浩斯间隔复习算法」，见 §8.3 问题② |
| 设备端语音走 ESP-SR（sherpa-onnx 不支持 ESP32） | ➖ 当前 13 项功能**未列语音**（喇叭仅做播放），暂不阻塞 |
| 双 OTA + 中文 TTS + 文件系统 > 16MB 的数学陷阱 | ⚠️ **需按实际 Flash 容量复核**，见 §8.3 问题① |

### 8.3 ⚠️ 实读中发现的 5 处待确认问题

| # | 问题 | 依据 | 影响 |
|---|---|---|---|
| **①** | **Flash/PSRAM 规格三处写法不一致**：`REQUIREMENTS.md` 写「DevKitC-N8R2（**16MB Flash + 8MB PSRAM**）」；`HARDWARE_DESIGN.md` 用封装 `ESP32-S3-DEVKITC-1-N8R8` 但正文写「承载 DevKitC-**N8R2**」；`HANDOFF.md` 也写 **N8R2**。而按乐鑫命名，**N8R2 = 8MB Flash + 2MB PSRAM**，16MB+8MB 对应的是 **N16R8** | 三份文档互不一致 | **影响很大**：2MB PSRAM 会限制 LVGL 双缓冲与音频缓冲；8MB Flash 会让「双 OTA + 音频/字库」非常紧张；文档 11 算出「双 OTA + 中文 TTS + 文件系统 > 16MB」。**请确认实际买的是哪一型**（N8R2 / N8R8 / N16R8） |
| **②** | **间隔复习算法用的是「艾宾浩斯」**（`REQUIREMENTS.md` 功能 1），不是 FSRS | 文档 11 与文档 04 均已核实：**FSRS 明显优于 SM-2 系**（log-loss 0.35 vs 0.45，约 22% 提升），且仅 21 参数、微秒级开销，**完全跑得动 ESP32** | 这是**零成本的算法升级**：同样做间隔复习，FSRS 的复习效率更高。建议改为 FSRS（或至少预留可替换的调度器接口） |
| **③** | **屏驱动 IC 是 ST7365**（冷门），而 `REQUIREMENTS.md` §五 自己就警告过要 datasheet 确认有库支持 | TFT_eSPI / LovyanGFX 对 ST7365 的支持需核实 | 若库不支持，需自己写 init 序列，或按 ST7796 驱动试跑（同族但不保证）。**建议下单前实测点亮** |
| **④** | **A2DP 发射**（功能 3 音乐播放器）：`REQUIREMENTS.md` §七 已自标「ESP32 原生不直接支持 A2DP 源发射」 | 需 ESP-ADF 或 pschatzmann 的 ESP32-A2DP（该库实际支持 source 模式，需核实） | 影响 BOM（是否需额外 DAC）与功能可行性 |
| **⑤** | **两处封装不符仍需修正**（`HARDWARE_DESIGN.md` §7）：U2 屏接口当前 2.0mm 间距但屏模块是 **2.54mm**（图中标注 2.54×8=20.32）；U3/U5 是 2.5mm XH 型但模块是 2.54mm 排针 | 文档 §7 问题 1/2 与 `HANDOFF.md` §5 P0-4 | **不改则成品插不上**，属必须修项 |

### 8.4 ESP32 端在整体系统中的定位（据实修正）

```
ESP32-S3 学习机（本机 13 功能，其中与学习系统直接相关的是①②⑦⑧⑨⑪）
├── 单词学习机（功能1）← 学习系统在弱端的主入口
│     ├── 本地 FSRS 排程（离线可用）
│     ├── 词库/卡片存 TF 卡（索引 + 数据分离）
│     └── 复习事件流缓存 → 与手机/PC 同步
├── 学习数据统计（功能11）→ CSV 导出
├── 番茄钟（9）/ 考试倒计时（8）/ 寝室模式（10）← 学习仪式感与自律
└── 电脑副屏（4）/ 数字小键盘（5）/ 计算器（2）← 非学习但共板

同步关系：ESP32 ⇄ 手机/PC（复习事件流），权威状态在手机/PC 合并
```

> 用户对 v0.5 的**目标级纠偏**：v2.2 把目标理解成「任意模型能读懂」，用户澄清真实目标是「**效果趋同**」。已落入**总框架 v2.3 §16**。

## 廿二、原话（逐字）

> 「我的意思是 我们的数据需要按照一种同一的格式来写 让多种模型在吃到前置提示词后再读取后面的资料出来的效果能差不多 而不是这个意思 这个统一的格式和架构是需要设计的」

## 廿三、纠偏说明（诚实记录）

| | v0.5（v2.2）的理解 | 用户澄清后的真实目标 |
|---|---|---|
| 目标 | 任意模型**能读懂**数据 | **同一前置提示词 + 同一格式数据 → 不同模型产出效果差不多** |
| 手段 | 三级手册（说明书范式） | **统一架构三件套**：统一数据格式 + 统一前置提示词 + 统一输出 schema |
| 验收 | 无 | **结构化字段机器比对必须一致**；语义等价人工抽检；文风允许差异 |
| 设计地位 | 附属说明 | **正式设计交付物**（「是需要设计的」） |

## 廿四、落点（框架 v2.3 §16）

| # | 内容 |
|---|---|
| 1 | **判定标准先行**：把「效果差不多」变成可验收——结构化字段必须一致（机器 diff）、语义等价（人工抽检）、文风允许差异 |
| 2 | **三件套**：`subject-pack/N`（数据怎么写）+ `prompt-pack/N`（怎么喂，**一份所有模型共用**）+ `output-schema/N`（怎么验）；同版本发布、互相引用 |
| 3 | **收窄自由度**：规程化步骤（不是「请你理解」）+ 输出 schema（枚举优先）+ **示例即 few-shot**（对齐跨模型效果最有效的单一手段） |
| 4 | **一份文本两种消费**：前置提示词 = 固定五段 + 注入 `阅读方法.md` 正文 + few-shot 示例；人读=手册、模型吃=提示词，**单一事实源不漂移** |
| 5 | **一致性验证循环**：多模型同题实测 → diff → 差异归类（语义差异=格式欠约束→收紧；字段缺失=补 schema；文风=允许）→ 版本+1 重测。**格式是「测」出来的，不是设计出来的**；弱/强模型结构化一致率达标（如 ≥95%）才接入便宜模型 |
| 6 | **端侧第 9 条规矩**：端侧不得改写前置提示词（只能选用版本，不能改内容） |
