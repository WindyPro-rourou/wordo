## ① 一句话结论

**ESP32 单词机这一端，能做的是「离线内容呈现 + 按键交互 + 轻量语音唤醒/命令 + 本地进度缓存 + 通过 WiFi/BLE 与手机同步」；不能做的是「大模型推理、任意中文 TTS 自由合成、通用语音识别、大词库实时检索」。**

具体切分：

- **ESP32 能独立承担的**：词条/卡片渲染与翻页、SM-2/FSRS 这类间隔重复调度（纯整数运算，KB 级内存）、本地错题与进度持久化（Flash/NVS/SD）、E-ink 或 TFT 显示、按键/旋钮/触摸交互、定时提醒、深度睡眠省电、ESP-NOW/MQTT/BLE 同步上报、**固定词表的语音命令识别（MultiNet，≤200 条）**、**唤醒词检测（WakeNet）**、**定字集中文语音播报（ESP-SR 语音合成 / esp32_tts，仅 ESP32-S3 + ≥8MB Flash）**。
- **必须放手机/PC 的**：新词内容生成与释义校对、爬取内容清洗入库、图像/语音大模型能力、自由文本 TTS（任意中文句子合成质量）、通用 ASR、词库的首次构建与分发、跨端冲突合并的权威裁决。
- **结论落到选型**：**首选 ESP32-S3 + 8MB PSRAM + 16MB Flash**（唯一同时满足 AI 向量指令、PSRAM 大缓冲、官方语音栈、USB OTG、成本可接受）。**ESP32 经典款已不再是新项目的选项**——乐鑫官方明确「新算法不再支持 ESP32」。

**两条必须先钉死的事实（否则架构会做错）**：

1. **sherpa-onnx 不支持 ESP32。** 官方平台表与构建脚本中没有任何 ESP32/ESP-IDF/FreeRTOS-MCU 目标（只有 RISC-V **Linux**、RK NPU、WASM、Android/iOS 等）。设备端语音只能用乐鑫 **ESP-SR**（WakeNet + MultiNet ≤200 命令词 + 中文 TTS，仅 S3）。
2. **FSRS 排程完全可以在设备端跑**（21 参数 / 微秒级，官方 wiki 核实）。→ **单词机可离线自主排程，同步时只交换复习事件流**，不依赖联网算调度。

### 2.2 AI 指令加速与推理能力边界

**乐鑫官方的态度（关键原文，✅ 一手，ESP-SR 组件页 v1.4.1）**：

> "ESP32-S3 is recommended, which supports AI instructions and larger, high-speech octal SPI PSRAM.
> **The new algorithms will no longer support ESP32 chips.**"

来源：https://components.espressif.com/components/espressif/esp-sr/versions/1.4.1?language=en

**这条直接决定了本项目不该选经典 ESP32。** 乐鑫新的语音/AI 算法栈已经放弃经典 ESP32。

- **ESP-NN**：乐鑫官方的 int8 SIMD 优化算子库，为 ESP32-S3 的向量指令服务。arXiv 论文实测在某 CNN 上 ESP-NN SIMD int8 kernel **286ms，比朴素卷积快 9.6×**（✅ 一手论文数据，但模型非本项目场景）：https://export.arxiv.org/pdf/2609.01683
- **ESP-DL**：官方深度学习推理库，含 `human_face_detect` 等现成模型（✅ 官方示例）：https://sengphirum.github.io/PLXY_DrowsyGuard/FIRMWARE_PIPELINE/
- **TFLite Micro 实测**：IEEE 论文，ESP32-S3 @80MHz 跑手势识别端到端 **180ms**（含量化感知训练 + 剪枝）（✅ 一手论文）：https://ieeexplore.ieee.org/abstract/document/11382541

**能力边界的现实判断**：
- 能跑：关键词识别、小分类器（手势/唤醒词/命令词）、极小 CNN（人脸检测、MNIST 级）。
- 跑不动：任何 LLM。即便 0.5B 参数的 int4 模型也远超 8MB PSRAM（0.5B × 0.5 byte ≈ 250MB）。**ESP32 上不存在"端侧 LLM"这条路**。
- 对单词机而言，端侧推理的真实用途只有两个：**唤醒词/命令词识别**、**发音评分或拼写纠错的轻量分类**。词义理解、例句生成必须回手机。

## ③ 外设选型表

### 3.1 显示屏：E-ink vs TFT/OLED

#### 核心矛盾（对背单词 UI 的直接影响）

E-ink 的**全刷会闪几次黑屏**、**局部刷不闪但会累积残影**——这是官方明确描述的机制：

> "Full refresh: The e-paper screen will flicker several times during the refresh process... the flicker is to remove the afterimage to achieve the best display effect.
> Partial refresh: The e-paper screen has no flickering effect during the refresh process."
> — ✅ 一手，Waveshare 官方手册：https://www.waveshare.com/wiki/4.2inch_e-Paper_Module_Manual

驱动层已在处理残影问题，官方例程对局部刷新做了反向补偿：

> "On partial update, set red RAM to inverse to remove BW ghosting"
> — ✅ 一手，ESPHome `epaper_spi_ssd1683.cpp` 源码：https://api-docs-beta.esphome.io/epaper__spi__ssd1683_8cpp_source

**对背单词 UI 的设计约束（重要）**：
1. **绝不能让每次按键都触发全刷**。翻一张卡片 = 一次局部刷（0.3s 量级）；每隔 20–50 次局部刷或切页/切模式时做一次全刷清残影。
2. **0.3s 局部刷 ≠ 瞬时**。它比 LCD 慢 10–50 倍。UI 必须"乐观更新"：先假设按键生效，不阻塞主循环。
3. **不要做进度条/动画/滚动**。E-ink 滚动列表会拖影，必须做整页翻页（分页而非滚动）。
4. **不要做倒计时秒表**。E-ink 刷新率撑不住连续数字变化。
5. 局部刷新区域有**对齐约束**（多数 EPD 控制器要求 x 按 8 像素对齐），布局要按 8 的倍数设计。

#### 屏幕选型结论

- **单词机的形态本质是「长时间静态显示 + 低频翻页」→ E-ink 是正确选择**，因为它零静态功耗（断电保持），这是续航的决定性因素。
- **推荐 2.9"（296×128）起步**：刷新最快（局刷 0.3s）、最便宜、SPI 简单、知乎/开源代码最多。296×128 能放下「1 个英文单词 + 1 行音标 + 2–3 行中文释义」。
- **4.2"（400×300）** 是"能放例句"的甜蜜点，但全刷 5s / 快刷 1.5s 明显更慢。若选它，UI 必须极度克制，全部交互走局部刷。
- **电子价签改造成本最低但坑最多**：便宜（¥10–40）但经常遇到私有排线、未知控制器、原厂固件锁、无资料。**DIY 第一版不建议从拆机价签起步**，会卡在引脚逆向而非业务逻辑上。

#### ⚠️ 重点核实：sherpa-onnx **不支持** ESP32

**结论：sherpa-onnx 无法运行在 ESP32 上（✅ 一手，官方仓库 README 逐项核对）。**

官方 README 的以下四个清单中，**均无 ESP32 / ESP-IDF / FreeRTOS-MCU**：

1. **Supported platforms 表**：Android / iOS / Windows / macOS / linux / HarmonyOS，架构只有 `x64`、`x86`、`arm64`、`arm32`、`riscv64`。
2. **Supported NPUs**：Rockchip RKNN / Qualcomm QNN / Ascend / Axera / Intel OpenVINO。
3. **"on the following platforms and operating systems" 列表**：x86/x86_64/32-bit ARM/64-bit ARM/RISC-V(riscv64)/RK NPU/Ascend NPU、Linux/macOS/Windows/openKylin、Android/WearOS、iOS、HarmonyOS、NodeJS、WebAssembly、NVIDIA Jetson、Raspberry Pi、RV1126、LicheePi4A、VisionFive 2、旭日X3派、爱芯派、RK3588、SpacemiT-K1/K3。
4. **构建脚本目录**：`build-android-*`、`build-ios*`、`build-macos*`、`build-ohos-*`、`build-riscv64-linux-gnu*.sh`、`build-rknn-linux-aarch64.sh`、`build-wasm-simd-*.sh`、`build-axcl-linux-aarch64.sh` —— **没有 `build-esp32*`**。

来源：https://github.com/k2-fsa/sherpa-onnx

**两个容易误判的点（必须澄清）**：
- ❌ **README 标题里的 "Support embedded systems"** 指的是 Raspberry Pi / RV1126 / LicheePi4A / RK3588 / SpacemiT-K1 这类 **跑 Linux 的嵌入式**，不是 MCU。ESP32 无 MMU、无 Linux、RAM 差 3–4 个数量级，跑不动 onnxruntime。
- ❌ **"Projects using sherpa-onnx" 里的 `xiaozhi-esp32-server`** 是**给 ESP32 设备提供后端服务的服务器端项目**。sherpa-onnx 跑在**服务器/PC 上**，ESP32 只是采集音频并推流的客户端。这**不能**作为"sherpa-onnx 支持 ESP32"的证据。

**对本项目的直接含义**：
- 设备端**不要**规划任何基于 sherpa-onnx 的能力（ASR / TTS / VAD / KWS）。
- 手机端（**iOS/Android 均官方支持 ✅**）可以放心用 sherpa-onnx 做离线 ASR/TTS/KWS —— 这正好落在"必须放手机"的分工侧。
- 设备端语音只能走 **ESP-SR**（下节）。
- 若真的想要"设备端通用 ASR"，唯一现实路径是：设备录音 → WiFi 把音频流推给手机/PC（跑 sherpa-onnx）→ 结果回传。

#### 中文离线 TTS：可行，但有硬约束

**可行**（✅ 一手，开源库仓库文档）：`@aily-project/lib-esp32-tts` v0.3.1
来源：https://github.com/ailyProject/aily-blockly-libraries/blob/main/esp32_tts/readme_ai.md

- **仅支持 ESP32-S3**（"Hardware: only ESP32-S3 is supported"）
- **要求 ≥8MB Flash**，安装时复制 `partitions.csv`，使用 **8MB 自定义布局 + 6.6875 MiB app 分区**
- 模型体积：**小模型约 2.78 MiB / 标准模型约 3.64 MiB**（编译期宏切换）
- 输出固定 **16kHz / 16bit / 单声道 PCM**，可 `MCLK = -1`（适配 MAX98357A）
- 支持：任意中文文本合成、拼音输入（`da4 jia1 hao3`）、金额播报、**6 档语速**
- **合成调用是阻塞式的**（"synthesis calls block"），需从另一个 FreeRTOS task 调 `stop()`

**这条路对本项目的意义**：单词机可以**离线读出英文单词/中文释义**，不需要联网、不需要手机。但注意：
- 3.64MB 模型 + 6.7MB app 分区 → **16MB Flash 几乎是必须的**（8MB 版会非常勉强，无法双 OTA）。
- 阻塞式合成 → UI 在播放时必须不卡死（用独立 task + 播放队列）。

**16MB Flash 分区建议**（参考官方与社区做法）：
```

phy_init, data, phy,      0xf000,   0x1000
factory,  app,  factory,  0x10000,  0x400000   # 4MB app（含 TTS 模型则需 6.7MB）
ota_0,    app,  ota_0,    0x410000, 0x400000   # 双 OTA
littlefs, data, spiffs,   0x810000, 0x7F0000   # 约 8MB 文件系统
```
来源参考（⚠️ 二手，16MB 分区 + 8MB LittleFS 实例）：https://twelite.net/manuals/twelite-spot/how-to-upload-firmware/esp32/partition/_print.html

## ⑤ 系统架构建议（ESP32 ↔ iOS/iPadOS ↔ Windows）

### 5.0 关键架构结论：**排程算法放设备端**

**FSRS 是纯数值调度算法，算力需求可忽略，ESP32 完全跑得动。**

核实到的参数规模（✅ 一手，open-spaced-repetition 官方 wiki）：
- **FSRS v4：17 个参数**
- **FSRS v6：19 个参数**
- **当前版本：21 个参数**（"This version uses 21 parameters. The memory state is represented by Stability (S) and Difficulty (D)."）
- 早期版本：7 个参数

来源：https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm ｜ https://github.com/open-spaced-repetition/fsrs4anki/wiki/The-Algorithm

> ⚠️ 父 agent 提到的「FSRS-7 约 34 个权重」**与官方 wiki 不一致**（wiki 最新列的是 21）。→ **标记为 ❓ 待核实**，但**无论 21 还是 34 个权重，结论不变**：每次调度只做几十次浮点乘加 + 一个指数函数，ESP32-S3 单次耗时在**微秒级**，相对 0.3s 的 E-ink 刷新完全无感。

**由此得出的架构决策（重要）**：
- **设备端自主排程**：ESP32 本地跑 FSRS，决定"下一张卡看什么、什么时候看"。**断网也能正常背单词**，这是碎片化复习场景的硬要求。
- **同步只交换「复习记录」而非「排程结果」**：上传的是 `(card_id, timestamp, rating, elapsed_ms)` 事件流，而不是"我算出你下次该在 X 时刻复习"。
- **服务端做权威合并**：手机/PC 收到事件流后重放（replay）到同一套 FSRS 参数上，得到权威的卡片状态。设备端只要拿到最新的 `(card_id → S, D, due)` 三元组即可。
- **为什么不用"服务端算好下发"**：设备离线时无法获得新排程 → 直接违背碎片化复习的产品前提。且反复 round-trip 增加功耗。

### 5.1 分工原则（能力边界表）

| 功能 | ESP32 单词机 | 手机 / PC |
|---|---|---|
| 卡片渲染与翻页 | ✅ | ✅ |
| FSRS 排程计算 | ✅ **主责** | ✅ 重放合并 |
| 复习记录持久化 | ✅ 本地队列 | ✅ 权威库 |
| 内容爬取 / 清洗 / 入库 | ❌ | ✅ **独占** |
| 词库构建与分发 | 只消费（SD/Flash） | ✅ **独占** |
| 发音音频合成 | ⚠️ 定字集可（ESP-SR TTS / esp32_tts） | ✅ 完整 TTS |
| 通用语音识别（跟读评测） | ❌ | ✅ |
| 唤醒词 / ≤200 条命令词 | ✅ **ESP-SR** | — |
| 大模型能力（释义生成、例句改写） | ❌ **完全不可能** | ✅ |

### 5.2 同步协议与数据流

```
[PC/服务器] 爬取 → 清洗 → 构建词库包(vocab.bin + 字库)
        │
        │  ① 词库下发（大、低频）：WiFi + HTTP(S) / SD 卡换卡
        ▼
[ESP32 单词机]  littlefs / SD 卡  ← 索引文件 + 数据文件分离
        │
        │  ② 学习时：本地 FSRS 排程 + 0.3s 局刷翻卡
        │  ③ 复习记录写本地队列（NVS / littlefs 追加日志，不频繁写裸 Flash）
        ▼
[手机 iOS/Windows]  ④ 拉取复习事件流 → 重放到权威 FSRS → 更新卡片状态
        │
        │  ⑤ 回写最新 (card_id, S, D, due) 快照到设备
        ▼
[ESP32 单词机]  更新本地卡状态
```

**协议建议**：
- **词库包**：`.bin` 二进制紧凑格式，**索引 + 数据分离**（学 SIPI2 的做法 —— 它用 Python 脚本把 ECDICT 转成「一个索引文件 + 一个数据文件」）。索引常驻 PSRAM，数据按需从 SD/Flash 读。
- **进度同步**：MQTT（有常连 WiFi 时）或 **BLE GATT 自定义特征**（手机在身边时）。事件流用 `card_id(uint32) + ts(uint32) + rating(uint8)`，**8–12 字节/条**，传输量极小。
- **时间**：设备无 RTC 时靠 SNTP（需 WiFi）或在同步时由手机校准；FSRS 的 `due` 必须用**绝对时间戳**，所以**设备必须能拿到可信时间**，否则离线期间排程会漂移。⚠️ 这是本项目的一个真实风险点。

| 加密模式配对上限 | **最多 6 个**（中文 FAQ）/ **≤17，默认 7**（英文 FAQ PDF） |
| 速率 | 可通过 `esp_wifi_config_espnow_rate` 配置 |

**结论**：
- ESP-NOW 适合「2–20 台单词机之间近场交换进度/排行榜」这种**小型局域网 P2P**，无连接、低延迟、不需要路由器。
- **不适合**作为去中心化大网络的通用节点：受 20 设备配对上限、无路由转发、单信道限制。
- 若要参与更大的去中心化网络（如本项目"去中心化分布式"主题），**ESP32 应定位为「边缘客户端」**：通过 MQTT/HTTP 和一个本地网关（手机或一台常开的 PC/树莓派）通信，由网关承担 P2P/libp2p 的协议栈。**ESP32 跑 libp2p 不现实**（协议栈 + TLS + DHT 内存开销远超可用 SRAM）。

## ⑥ 坑与风险

### 6.1 E-ink 刷新
1. **全刷闪屏**：官方明确全刷会"flicker several times"。若每次按键全刷，用户体验是"屏幕疯狂闪"，不可接受。
2. **局刷残影累积**：必须定时/计次清残影。ESPHome 的处理是"局刷时把 red RAM 设为反相以去除黑白残影"——说明残影是**必然现象**，只能补偿不能消除。
3. **刷新区域对齐**：多数 EPD 控制器要求 x 坐标 8 像素对齐，布局要迁就。
4. **低温变慢**：E-ink 在低温下刷新显著变慢（❓ 待核实具体曲线），户外冬季使用需实测。
5. **排线易断**：大尺寸 E-ink（7.5"）FPC 排线脆弱，DIY 反复拆装易损。
6. **不能做动画/滚动/秒级计时**。

### 6.2 内存不足
1. **ESP32-S3 无 L2 cache**，每次访问 PSRAM 付约 **80ns** 延迟（⚠️ 二手实测讨论）。→ **热路径数据必须放内部 SRAM**，PSRAM 只放大块缓冲（帧缓冲、音频、字库缓存）。
2. **帧缓冲吃掉大量内存**：400×300 单色 = 400×300/8 = **15KB**（可接受）；若上灰度/彩色则翻数倍。
3. **TTS 模型 2.78–3.64MB + LVGL + WiFi 协议栈同时存在**，2MB PSRAM 版会非常紧张。
4. CrossPoint Reader 的实测结论值得抄：ESP32-C3 只有 **~380KB 可用 RAM**，所以"**非常激进地把数据缓存到 SD 卡**"以降低 RAM 占用。

### 6.3 字库体积
- HZK16 全 GB2312：约 **216KB**；HZK24：约 **487KB**（按 32B / 72B 每字推算）。
- 若上 **LVGL + 矢量字体（如 simhei.c）**，体积会显著膨胀（SIPI2 直接内置 `simhei.c`）。
- **字体子集化是必须的**：如果只用 5000 常用词，可以先提取语料中出现的所有汉字，做子集化字库，通常能把字库压到原体积的 20–40% ❓。
- **词库体积估算**（关键，❓ 需实测）：5000 词 × (单词 ~10B + 音标 ~30B + 释义 ~60B + 例句 ~150B) ≈ **1.25MB 纯文本**；若含多条例句与词形变化，保守按 **2–4MB** 估算。压缩后（zstd/自研定长索引）可显著减小，但**解压需要 RAM**。

### 6.4 MicroPython 陷阱
实测空闲堆对比（✅ 一手，esp32-lang-lab 仓库基准）：

| 语言/框架 | Free heap (bytes) |
|---|---|
| ESP-IDF C | **300,892** |
| Rust std | 296,028 |
| Arduino | 237,568 |
| Rust no_std | 179,200 |
| **MicroPython** | **164,064** |
| **CircuitPython** | **113,424** |

来源：https://github.com/georgik/esp32-lang-lab

- MicroPython 可用堆只有 ESP-IDF C 的 **约 55%**；CircuitPython 只有 **约 38%**。
- 另有对比资料给出：MicroPython Flash 开销 **~1.5MB**、基础 RAM 开销 **~160KB + heap**，且为**解释执行（慢）**（⚠️ 二手）：https://electricalflux.com/mcu-projects/esp32-programming-language-cpp-micropython-rust
- **MicroPython 只适合原型验证**。一旦要上 LVGL 大 UI + 字库 + FSRS + 语音，必须回 C（ESP-IDF）。官方 MicroPython ESP32 port README 也说明：无 SPIRAM 的板子"may run out of RAM if a program uses a lot of resources"（✅ 一手）。

### 6.5 烧录与 OTA（SIPI2 的真实教训）
- **Dual OTA 分区会吃掉一半 app 空间**。SIPI2 给出了血的教训细节：自制板不集成 USB 串口芯片，需要短接特定引脚才能烧录；**键盘扫描用了独立 STC8H1K28 单片机，需要分别烧录 ESP32 和 STC8**，且 STC8 有"复位脚当 IO 后下次烧录要先点烧录再复位"的坑。
- → **反面教材：不要为了省几个引脚加第二颗 MCU。** 键盘矩阵用 ESP32 自己的 GPIO + 二极管/IO 扩展（如 TCA9535）直接扫描。
- **16MB Flash + 双 OTA + 中文 TTS(6.6875MB) 在数学上不够**，必须 32MB 或外挂 SD。

### 6.6 其他
- **NVS 写寿命**：每次翻卡都写 NVS 会磨穿 Flash（约 10 万次擦写）。→ 用追加日志 + 批量落盘。
- **iOS 兼容性**：BLE 自定义 GATT 在 iOS 上可行，但**后台传输受限**，需 App 在前台完成同步。
- **WiFi 功耗**：常连 WiFi 会让续航从"月级"掉到"天级"。→ 默认关 WiFi，仅同步时开。

## ⑦ 对本项目的 5 条可落地建议

### 建议 1：第一版原型就买 **ESP32-S3 + 8MB PSRAM + 16MB Flash 的开发板**，不要从拆机电子价签起步

具体推荐（按 DIY 友好度排序）：
- **首选：LilyGO T-Display-S3** 或 **LilyGO T5 4.7" E-Paper S3** —— 社区资料多、PSRAM 8MB、自带屏幕，能一周内跑起 UI。
- **次选：Waveshare ESP32-S3 驱动板 + 2.9" E-ink 模块** —— 官方例程齐全（含局刷），最容易复现"0.3s 局刷翻卡"。
- **参考整机形态：ZecTrix Note4**（ESP32-S3 + 4.2" EPD + ES8311 音频 + 按键 + 电池，ESP-IDF 5.5.x 固件，社区有多个开源固件可参考）：https://wiki.zectrix.com/zh/software/Community-OpenSource-Firmware

**不要**第一版就上电子价签拆机屏：便宜但会卡在引脚逆向/未知控制器/原厂固件锁上，把时间烧在硬件考古而不是产品逻辑上。

### 建议 2：**FSRS 放设备端**，同步只交换复习事件流

- ESP32 本地跑 FSRS（21 个参数，微秒级开销），**离线自主排程**。
- 上传 `(card_id, ts, rating)` 事件流（8–12 字节/条），由手机/PC 重放合并。
- 设备只需从云端拿回 `(card_id → S, D, due)` 快照。
- **必须解决时间源问题**：SNTP 或在同步时由手机写入 RTC/软件时钟，否则离线排程会漂移。

### 建议 3：抄 **SIPI2** 的「索引 + 数据分离」词库方案，并抄它的数据源

SIPI2 是一个**已经成功的同用途参照**（MIT 协议，软硬件全开源）：
- 主控 **ESP32-WROOM32**（经典款！证明经典款"能跑"词库，但跑不了语音/AI）
- **1.77" TFT ST7735S，160×128，SPI**
- **SPI/SDMMC 内存卡存单词内容**
- 词库来自 **skywind3000/ECDICT**（免费英汉词典数据库），用 Python 脚本预处理成**一个索引文件 + 一个数据文件**
- UI 用 **LVGL**，ESP-IDF v4.4.2
- 30 余个按键全键输入（键盘扫描交给独立 **STC8H1K28** 经串口上报）
- 电源：**IP5306CK**（2.1A 充电 / 2.4A 放电 SOC）+ **XB7608AJ** 锂电保护
- 内置中文字体 `simhei.c`
- 功能：查词、蓝牙 HID 键盘（连手机/电脑）
- 仓库：https://github.com/SendToSouthEast/SIPI2

**直接建议**：词库预处理管线照抄 SIPI2 的结构（Python 把 ECDICT → 索引 + 数据），**但把主控换成 ESP32-S3（保留语音与 PSRAM 余量），把 STC8 键盘协处理器删掉**。

### 建议 4：语音能力走 **ESP-SR（WakeNet + MultiNet）**，放弃在设备上跑通用 ASR/TTS

- **明确核实结论**：**sherpa-onnx 不支持 ESP32。** 官方 README 的 Supported platforms 表只列 Android / iOS / Windows / macOS / Linux / HarmonyOS + x86_64 / x86 / arm64 / arm32 / **riscv64**，构建脚本只有 android / ios / macos / ohos / riscv64-linux / rknn-linux / wasm / axcl-linux —— **没有任何 ESP32 / ESP-IDF / FreeRTOS-MCU 目标**。README 标题里的 "embedded systems" 指 Raspberry Pi / RV1126 / LicheePi4A / RK3588 这类 **Linux 嵌入式**，不是 MCU。
- 常被误解的点：`sherpa-onnx` 的使用者列表里有 **`xiaozhi-esp32-server`**，但那是**给 ESP32 设备提供后端服务的服务器端项目** —— sherpa-onnx 跑在**服务器/PC 上**，ESP32 只是推流音频的客户端。
  - 来源：https://github.com/k2-fsa/sherpa-onnx
- → **设备端语音实际可用的只有乐鑫官方栈**：WakeNet（唤醒词）+ MultiNet（≤200 条命令词）+ AFE（AEC/VAD/NS）+ **中文 TTS（仅 ESP32-S3，需 ≥8MB Flash）**。
- → **跟读打分、任意中文语音合成、通用 ASR 全部放手机/PC**（手机端可以用 sherpa-onnx，它支持 iOS/Android ✅）。

### 建议 5：UI 用 **LVGL + 8 像素对齐布局**，交互模型定死为「翻页 + 4 个物理键」

- **UI 铁律**：分页不滚动、翻卡用局刷、每 N 次局刷做一次全刷清残影、不做进度条/动画/秒级计时。
- **按键**：4–6 个物理键（认识 / 模糊 / 忘记 / 上一个 / 发音）比触摸屏更适合 E-ink（触摸会误触且增加功耗）。参照 ZecTrix Note4 的按键+电池形态。
- **LVGL + `lv_fs_if` + SD 卡**已被 SIPI2 验证可行（ESP-IDF 组件结构：`lvgl` / `lvgl_esp32_drivers` / `lv_fs_if` / `sdcard_init`）。
- **功耗目标参考**（⚠️ 二手实测）：
  - reTerminal E1003（ESP Home，E-ink）：醒着空闲 **~185mA**，深睡 **4–5mA** → 实机续航 **约 20–30 天**：https://github.com/ar0v3r/reTerminal-E1003-ESPHome
  - Inkplate 13 SPECTRA：**3000mAh + 每小时全屏刷一次 → 约 40–50 天**：https://www.crowdsupply.com/soldered/inkplate-13spectra
  - ESP32-S3 深睡（RTC timer）**8µA**（⚠️ 半官方）
  - → 按「每天背 30 分钟」估算：**若 WiFi 常关、只在同步时唤醒，2000mAh 电池做到 2–4 周量级是合理预期**（❓ 需实测，取决于 WiFi 同步频率与 E-ink 刷新次数）。

### 先验知识（未经检索，待核实）

- ESP32 经典款：Xtensa LX6 双核 240MHz，520KB SRAM，通常配 4MB Flash，无原生 USB，WiFi 4 + BLE 4.2。
- ESP32-S3：Xtensa LX7 双核 240MHz，512KB SRAM + 可选 2/8MB PSRAM，带 **向量指令扩展（Vector Extension）** 专为 AI 加速，原生 USB OTG，WiFi 4 + BLE 5.0。
- ESP32-S2：LX7 单核 240MHz，无 BLE（只有 WiFi），USB OTG，AI 能力弱。
- ESP32-C3：RISC-V 单核 160MHz，400KB SRAM，WiFi 4 + BLE 5.0，成本极低，无 PSRAM，不适合 AI。
- ESP32-C6：RISC-V 单核 160MHz（高性能核）+ 低功耗核，支持 WiFi 6 + BLE 5 + Thread/Zigbee，512KB SRAM。
- ESP32-P4：RISC-V 双核 400MHz + 低功耗核，768KB SRAM + 可选 PSRAM，**无 WiFi/BLE**（需外挂 C6 等协处理器），带 MIPI-CSI/DSI、H.264 编解码、AI 指令扩展。
- E-ink 全刷通常 1–3 秒（视尺寸/温度），局部刷 0.2–0.5 秒，有残影（ghosting）问题。
- sherpa-onnx 官方支持平台以桌面/移动为主，ESP32 端 **存疑**，需核实。
- ESP-SR 是乐鑫官方语音识别框架，含 WakeNet（唤醒词）、MultiNet（命令词）、AEC、VAD，主要面向 ESP32-S3/ESP32。
- ESP-DL 是乐鑫官方深度学习库，配合 ESP-NN 优化算子，面向 ESP32-S3 的向量指令。
- TensorFlow Lite Micro 有 ESP32 移植，但经典 ESP32 内存吃紧。
- 中文 5000 常用词 + 释义 + 例句，纯文本压缩前大致 1–3MB 量级，需实测。
- 中文点阵字库：完整 16x16 GB2312 字库约 260KB，24x24 约 580KB，全 Unicode CJK 会到 MB 级。
- ESP-NOW 是无连接 WiFi 私有协议，适合设备间低延迟小数据量通信，可做 P2P 节点但需处理信道/配对。
- TP4056 是线性锂电充电 IC（1A，SOT-23-5 + 外部电阻），IP5306 是移动电源 SoC（2.4A，集成升压 + 电量计）。
