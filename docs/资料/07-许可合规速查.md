# 07 · 许可合规速查（依赖与借鉴的红线）

> 调研时间：2026-10-26 ｜ 用途：决定「哪些代码能抄、哪些只能读思路、哪些能当依赖」
> ⚠️ 本文为工程速查，**不构成法律意见**。商业发布前请咨询法务。判定依据：FOSSA License Compatibility Checker。

---

## 一、核心规则（一句话）

**许可证的兼容性有方向性：宽松（permissive）可以被吸收进强著佐权（copyleft），反之不行。**

| 方向 | 结论 | 依据 |
|---|---|---|
| **Apache-2.0 代码 → 放进 AGPL-3.0 项目** | ✅ **兼容**。保留原始版权与许可声明；**合并后的整体作品必须以 AGPL-3.0 分发** | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/apache-2-0-vs-agpl-3-0/> |
| **AGPL-3.0 代码 → 放进 Apache-2.0 / MIT 项目** | ❌ **不兼容**。强著佐权无法被宽松许可「包住」 | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/agpl-3-0-vs-apache-2-0/> |
| MIT / BSD-3 → AGPL-3.0 | ✅ 兼容 | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/mit-vs-agpl-3-0/>、<https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/bsd-3-clause-vs-agpl-3-0/> |
| MPL-2.0 → AGPL-3.0 | ⚠️ 有条件 | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/mpl-2-0-vs-agpl-3-0/> |
| GPL-3.0 → AGPL-3.0 | ✅ 兼容 | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/gpl-3-0-vs-agpl-3-0/> |
| Apache-2.0 → GPL-2.0-only | ❌ 不兼容（专利条款冲突） | <https://fossa.com/resources/license-compliance-tools/license-compatibility-checker/apache-2-0-vs-gpl-2-0/> |

**AGPL-3.0 的关键特性**：网络著佐权——**通过网络提供服务（SaaS）也会触发源码开放义务**（堵住「SaaS 漏洞」）。这是与 GPL 最重要的区别，对「去中心化/多端服务」形态的项目影响极大。

## 三、本项目的许可策略建议

### 选项 A：本项目采用 **AGPL-3.0**（推荐用于「开源 + 防止被闭源白嫖」）
- ✅ 可吸收所有 Apache-2.0/MIT 的成果（ReMe、GSV、TOPLOC…）。
- ✅ 仍**不能**直接抄 Continuum 的代码吗？——**可以抄**（同为 AGPL），但必须满足 AGPL 的全部义务（含网络服务开源）。
- ⚠️ 代价：任何集成本项目的产品（含 SaaS）都必须开源；不利于被商业集成。

### 选项 B：本项目采用 **Apache-2.0 / MIT**（推荐用于「最大化被采用」）
- ✅ 可吸收 ReMe、GSV、TOPLOC、llama.cpp 等宽松许可成果。
- ❌ **绝对禁止**复制 Continuum（AGPL）或任何 AGPL/GPL 代码——**只能读架构、抄思想**。思想（架构模式、算法思路、术语）本身不受版权保护，但代码、文档原文、注释、配置文件都受保护。
- ⚠️ 若引入 AGPL 依赖，整个项目被迫 AGPL。

### 选项 C：双许可 / 分模块
- 核心引擎用 AGPL-3.0，SDK/契约层用 Apache-2.0（类似很多开源商业项目做法）。复杂度高，小团队不建议起步就用。

### 我们的建议
**起步阶段选 A（AGPL-3.0）**，理由：本项目天然是「网络服务 + 多端」，AGPL 与该形态最自洽；同时它让我们可以合法吸收 Continuum 的经验（若确实需要借鉴其实现细节）。若后续需要被商业友好集成，再考虑分模块双许可。

> ⚠️ 注意 AGPL 的**反向约束**：一旦选 A，就必须在 README 与「关于」页面明确声明，并且**网络服务的使用者有权获取源码**。这在设计 API 与部署形态时就要预留。

## 四、合规操作清单（每次引入外部代码时执行）

- [ ] 在 `THIRD_PARTY_NOTICES.md` 记录：项目名、仓库 URL、许可、引入版本/commit、引入方式（依赖 / 复制代码 / 仅参考）。
- [ ] 复制代码时**保留原始版权头与许可文本**。
- [ ] 建立依赖扫描（CI 中跑 `license-checker` / `pip-licenses` / `cargo-deny` / FOSSA 等），防止**传递依赖**带进不兼容许可。
- [ ] 区分三档并明确记录：**①可直接依赖 → ②可复制代码（需声明）→ ③仅可参考思路（不得复制）**。
- [ ] 「仅参考思路」的项目要写进文档黑名单，避免后续贡献者无意复制。
- [ ] AI 生成代码也要过一遍许可扫描（模型可能复现训练数据中的受保护代码）。
